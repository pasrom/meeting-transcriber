# Recording

Dual-source capture: start order, restarts, tap and microphone behaviour, channel faults.

**Recording:**
- `DualSourceRecorder` uses `AudioTapLib.AudioCaptureSession` directly (no subprocess). App imports the library via SPM local package dependency.
- `DualSourceRecorder` captures `recordingStartTime` in `start()`, not in `stop()`.
- Grace period minimum is 1 second (enforced in `AppSettings.endGrace` setter).
- **Start order (issue #693):** `AudioCaptureSession.start()` opens the microphone **before** the app tap, and the order is load-bearing: opening the input takes a Bluetooth headset out of A2DP into its call profile, and with the tap first that disturbance landed underneath an aggregate device that had been created and started but had not yet run its first IO cycle, leaving the tap delivering nothing for the whole recording (no callback, zero bytes, no error). Measured: 9 failures in 30 starts with the tap first, 0 in 30 with the microphone first, which bounds the remainder rather than proving it gone. Two consequences in the code: a microphone failure is swallowed when an **app track was requested** (not when an app capture is already running, which after the move it never is), and a failed start removes both output files it created, since an empty app temp is the crashed-recording signature and a stray `_mic.wav` is collected by nothing. **The rest of the argument lives in one place, the doc comment on `AudioCaptureSession.start()`: what the order does and does not guarantee, the three accepted costs (a wedged first start, now bounded and costing the microphone, the restart paths, app-only recordings), and the follow-up all three want.** `micDelay` is now normally negative, which `MicDelayNormalisation` absorbs.
- **Capture-restart bounding (issue #588):** a device-change restart on either channel can wedge inside AVFAudio/CoreAudio and never return (e.g. `AVAudioEngine.inputNode` looping on a dangling Bluetooth sub-device). `RestartArbiter` bounds how long a single restart attempt may run (generation-tagged, off-main-queue) so a wedged attempt can't freeze the app or have its stale result adopted; `CaptureRestartRetryPolicy` bounds how many attempts are made, shared by both channels. A channel that gives up notifies the user directly instead of only decaying to silence, which the asymmetric-silence detector would otherwise misreport as a mute/routing problem. **The microphone's first start is bounded the same way (issue #778):** `MicCaptureHandler.start` runs the first `startEngine` on the restart queue as an arbiter attempt, and the main queue waits for it for `RestartArbiter.attemptTimeout` plus at most `firstStartReportGrace` (0.5 s, only when the deadline and the attempt's report cross), through a timed group wait (`awaitFirstStart`) rather than `scheduleOnMain`, whose timer could not fire on the thread that waits. On expiry it throws `MicCaptureError.firstStartTimedOut` and arms neither the progress watch nor the device observers; a dual-source recording goes on with the app track and reports it as a give-up with `micCaptureStartTimedOut`, which selects its own notice text (only what was observed, no remedy). Every attempt, first start or restart, checks that it is still the current one before its first engine call, again before `installTap` (an early exit: a tap only attaches to a node) and before `start`, the one step that opens the input, so a call that returns after its deadline, with or without a stop, installs no tap and opens no input (which would switch a Bluetooth headset's profile under whatever records then); the file and converter steps between the checks are not checked. A stale first start removes the recording's file only if it created it. What is left: a step that passed its check and itself takes longer than the deadline still opens the input late, until the stale attempt is torn down when it returns; and the thread stays in its call for as long as the call takes. Not measured: how long a healthy first start takes on every device, so whether five seconds always suffices (a Bluetooth profile switch, a first permission prompt) is open, and so is whether AVFoundation hops to the main queue internally while it waits.
- **Safari support (issue #524):** the app-audio tap also targets processes via macOS's *responsible-process* attribution (`ProcessResponsibility`), since Safari's call audio comes from WebKit XPC services outside `Safari.app` rather than child processes under its bundle (the existing `ProcessTreeEnumerator` path Electron/Teams use). Resolved via `dlsym` on a private symbol, so it compiles to `nil` under `APPSTORE` — a conscious tradeoff that leaves the sandboxed build without Safari call capture (see Build Variants in `CLAUDE.md`).
- **App-track capture rate (issue #683):** `AppAudioCapture.resolveActualSampleRate` resolves the rate the tap is captured at from the private aggregate's own properties (`SampleRateQuery.chooseRate`): the nominal rate when it can be read, the requested default otherwise. **The output-stream format never decides on its own**: it corroborates the nominal rate, and its disagreement is a warning, but a lone answer from it falls back to the requested rate, because it is the property that reports a Bluetooth HFP link rate (#82). Both properties are read every time, since the disagreement warning needs both, and the result is logged with its rung on the `Created aggregate device: N, rate … Hz (nominal and stream agree), default 48000 Hz` line. There is deliberately no rung for the tap's own format: a `CATapDescription(stereoMixdownOfProcesses:)` tap reports a fixed 48 kHz at every device rate (measured at 44.1, 48 and 96 kHz), and placed on top it made the two real rungs unreachable. "Requested" is only the fallback: nothing asks the aggregate for a rate, it takes its main sub-device's, so a 44.1 or 96 kHz device is normal and not warned about. Two corrections layer on top: the first-callback `kAudioDevicePropertyActualSampleRate` read (covers creation to first buffer, when a Bluetooth headset may flip profile) and `DeliveredRateTracker` (in-place changes after that). A `Measured rate … differs from cached` warning therefore means the aggregate changed rate between creation and start, not that the device is at 44.1 or 96 kHz. Manual check on a non-48 kHz device: set the output to 96 kHz in Audio MIDI Setup, record one meeting-simulator run, then `log show --last 5m --predicate 'subsystem == "com.meetingtranscriber.audiotap"'`; expect `rate 96000 Hz (nominal and stream agree)` on the aggregate line, no `Measured rate` warning, no tracker `delivering … not the published` line, and an app track the length of the fixture. Restore the device rate afterwards and read it back.
- **Chromium helper selection (issue #791):** a Chromium browser or Electron app renders all its audio in one utility helper (`--utility-sub-type=audio.mojom.AudioService`), but the bundle walk and the responsibility grouping also return helpers that merely talked to CoreAudio. Measured on macOS 14.6.1: a tap over the audio service *and* the video-capture service never ran its first IO cycle (tap, aggregate and `AudioDeviceStart` all succeeded; the aggregate stayed not running), while the audio service alone or with the browser root delivered. `ChromiumHelperFilter` reads each candidate's argv (`KERN_PROCARGS2`, `ProcessArguments`) and, once an audio service is among them, keeps only it and the processes without a `--type=` flag (the root, anything non-Chromium). No audio service found, or argv unreadable: the set is left alone, so native apps, Safari's WebKit helpers and a Chromium with in-process audio are untouched. The dropped helpers are logged next to the tap summary. The underlying HAL interaction is not understood; the filter removes a process that cannot be the audio source either way.
- **The tap is the aggregate's last input buffer (issue #803; mechanism behind #712 and #699):** the private aggregate binds the system default output device as its only sub-device, and when that device also has inputs (an audio interface, a USB speakerphone or headset, a loopback/virtual device such as the Teams loopback driver), the aggregate exposes those input streams ahead of the tap's: the IOProc then gets one buffer per stream, the device's own input first and the stereo-mixdown tap last. `AppAudioCapture.tapBuffer(in:)` therefore takes the last buffer: with such a default output the first is the device's input (an ADC floor, a speakerphone's microphone, whatever other apps play into a loopback device), not the meeting, regardless of which device the meeting app rendered to. **The anchor device does not decide what the tap hears** (a `stereoMixdownOfProcesses` tap follows the process); it decides only how many buffers precede the tap. The layout is logged three ways, counts only, no device identity: `Aggregate input layout: anchorInputs=A inputStreams=N, tap is the last stream` at every tap build (start and each restart, before the device starts; a warning ending `the last buffer may not be the tap (#712)` when `N != A + 1`, a warning ending `no input stream at all, so no tap stream to read` when `N = 0`, and `?(status)` with `could not tell …` when a read failed), `inputStreams=N` on every `App audio device (start|watchdog check|zero run started|stop)` line (after the device started, so a headset that gains an input stream mid-call without a default-output change shows as two different numbers), and `N buffers (tap is the last)` on the first-buffer `Audio format:` line. "Last" rests on the aggregate holding exactly one tap stream, measured on one interface so far; a field log with `N != A + 1` is the first evidence against it.
- **Mic channel-map fix:** `MicChannelMap`/`MicConverterFactory` force an explicit channel selection for any mic layout other than mono or plain stereo — `AVAudioConverter`'s implicit downmix silently writes digital silence for most tagged layouts, including 2-channel mic-pair ones (MidSide, XY, StereoHeadphones). The policy is an allowlist, not a discrete-layout special case: anything outside it takes channel 0. Reachable in practice when another app's voice processing switches the built-in mic to a multi-channel array mid-call.
- **Pinned mic tap format (issue #724):** after `MicEngineSession` points the input unit at `AppSettings.micDeviceUID`, `inputNode.outputFormat(forBus: 0)` keeps answering the format of the system default input the engine was bound to, while `inputFormat(forBus: 0)` answers the device the unit is on; a tap built from the stale side installs and never delivers. `hardwareFormat` therefore reads the input side whenever `MicDevicePinOutcome.wasAccepted` (any accepted set, adopted or not — the output side is stale either way), and the unpinned path is unchanged. The measurement, and what it has not yet confirmed, is recorded on `wasAccepted`.
- **Mic mute during a recording:** a mute silences this recording only, not the call. `MicCaptureHandler` keeps the engine running and zeroes each buffer after conversion, so tracks stay aligned and live captions receive silence; reopening the input instead risks the Bluetooth profile flip and restart wedge (#693, #588). The level is published before the zeroing, so `ChannelHealthMonitor`, `SilentRecordingMonitor` and `ChannelFaultMonitor` stay quiet and a dying app tap is still corroborated; `/state` hides that level while muted. The macOS mic indicator stays on. `AppSettings.startRecordingsMicMuted` applies to app recordings only, and no mute carries over between recordings. The hotkey (`GlobalHotkeyRegistrar`, Carbon, no permission) is registered only while a recording can be muted; the menu item shows it, or ⌘M when none is set. What the pipeline does with the mute times is in `pipeline.md`.
- **Channel fault vs. channel quiet (issue #614):** `ChannelHealthMonitor` (levels, with hysteresis) answers "is this channel unusually quiet compared to the other", the right question for the menu-bar red-half tint but the wrong one for a notification — a muted or simply non-speaking participant is quiet and that is normal call etiquette, not a broken capture. `ChannelFaultMonitor` answers "is this channel still delivering" from the per-buffer ages the capture layer reports (`ChannelSignalAges`) rather than from a level, and drives the "Capture Channel Silent" notification instead. Buffers stopping entirely is reported unconditionally; digital silence (buffers arriving but all-zero) is reported only when corroborated by the other channel still carrying signal, since all-zero samples are also what a healthy channel carries when its source has nothing to say. The tint (levels) and the notification (ages) can therefore disagree by design. **The app channel's message depends on whether it ever carried a non-zero sample in this recording** (`everCarriedSignal`, read from `ChannelSignalAges.secondsSinceLastEnergy != nil`). A tap that is not allowed to hear the app returns `noErr` and then delivers zeroes from its first buffer and never anything else (issue #524, and there is no preflight API for that grant), so a channel that carried audio and then went to zeroes cannot be a permission problem and must not be sent to the Screen Recording pane; one silent since the first buffer very well might be, and keeps that advice. Buffers stopping altogether is a third case, and the honest thing to say about it is less than it is tempting to say: what #524 measured is a tap denied *from the start*, which delivers zeroes rather than nothing, so whether revoking the grant mid-recording stops the IOProc is not established and `ChannelFault.noBuffers` still lists it as a possible cause. That message therefore claims neither way and names the remedy instead. It also drops the "while the microphone is still recording" clause the other two carry: `digitalSilence` needs corroboration from the other channel before it is reported at all, so the clause is true there by construction, while `noBuffers` is reported unconditionally and an app-only recording (`RecordingSource.appOnly`) has no microphone. The two app messages that a user can act on name the one lever there is, switching the system output device, because that is the only thing that rebuilds the tap today. They name **where** to pull it (Control Center, or `SystemSettingsPaths.soundOutput`) and where not to: the rebuild is triggered by a change of `kAudioHardwarePropertyDefaultOutputDevice`, so an output chosen inside the meeting app's own speaker picker never fires it, and that picker is the one in front of the user during a call. **`noBuffers` claims nothing about the past**, on either channel: the monitor reads `ages.secondsSinceLastBuffer ?? elapsedSinceStart`, so the fault covers a channel that never delivered a single buffer exactly as it covers one that delivered and then stopped, and the never-started case is the whole of #693. Both messages therefore state the present; the one arm where a past delivery is guaranteed is `digitalSilence` with `everCarriedSignal` true, and only that one says so. They also stop at **one** switch rather than "and back": a second rebuild rolls the same dice the first one did, and a field report has a freshly started capture failing identically to the one before it with nothing changed. The microphone's two messages ignore the flag. **A floor below one 16-bit step is its own fault (issue #699):** a tap anchored where the meeting app does not play can deliver a constant floor of about -98.5 dBFS that never reaches an exact zero, so every buffer counts as energy and `digitalSilence` never fires. `AppNoiseFloorSensor` (AudioTapLib, app tap only) reads the per-buffer sum of squares `accumulateDebugRMS` already computes and holds `appCarriesOnlyNoiseFloor` once a full 120 s window is at least 90% samples from buffers whose RMS is below 2^-15, clearing at 50%. `ChannelFaultMonitor` turns that into `ChannelFault.noiseFloor` under the same window, microphone corroboration and once-per-recording silence latch as `digitalSilence`, which keeps precedence for a window of exact zeros. The shared energy definition (`LevelPublisher`'s `hasEnergy`, read by the microphone channel and the silent-track watchdog) is deliberately unchanged, and nothing re-anchors or rebuilds the tap: the sensor only warns. `/state.channelHealth.appNoiseFloorOnly` is its live, uncorroborated reading.
