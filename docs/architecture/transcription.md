# Transcription and live captions

ASR engines, WhisperKit model handling, vocabulary, live captions and VAD.

**Rule for every WhisperKit call that can download or load a model:** pass `downloadBase: WhisperKitLocalSnapshot.downloadBase`. Without it the library silently writes into `~/Documents/huggingface`, which iCloud can sync (issue #640). Use `downloadBaseLocation` only for a read that must not create the folder.

**Transcription engines:**
- `TranscribingEngine` protocol abstracts ASR backends. Two implementations: `WhisperKitEngine` (99+ languages, ~1 GB model) and `ParakeetEngine` (25 EU languages, ~50 MB model, ~10× faster).
- `AppSettings.transcriptionEngine` enum (`.whisperKit` / `.parakeet`) selects the engine. Settings UI shows engine picker; engine-specific options hidden when not selected. `availableCases` (filtered by `isAvailable`) is the picker source — a capability hook kept for engines with stricter OS floors.
- Parakeet auto-detects language (no parameter). WhisperKit supports explicit language selection.
- **Custom vocabulary** is one shared one-term-per-line file (`AppSettings.customVocabularyPath`, resolved through `VocabularyFileAccess` for sandbox bookmark access) used by both engines, not a Parakeet-only setting. One switch, `AppSettings.customVocabularyEnabled` (Settings → Transcription → Vocabulary, "Use custom vocabulary"; the file row is hidden while it is off, an ⓘ `HelpBadge` beside it explains it on hover, adding the experimental warning while WhisperKit is selected rather than showing captions), decides whether either engine reads it: off, Parakeet gets an empty path from `EngineController` and WhisperKit's `vocabularyPromptEnabled` is false. An upgrade without the key starts it where the engine in use was (`initialCustomVocabularyEnabled`): for WhisperKit the old `whisperKitVocabularyPromptEnabled` flag, for Parakeet whether a file is set. It is derived once, so it only preserves behaviour for that engine: a Parakeet user with a file who later picks WhisperKit gets the experimental prompt on, and a WhisperKit user with the old flag off who later picks Parakeet gets no boosting (an `||` of both would turn the WhisperKit prompt on for everyone with a file). On, Parakeet applies the file via CTC boosting and WhisperKit via `WhisperVocabularyPrompt` turning the file into a bounded decoder-prompt hint, where the 32-token budget keeps the earliest terms (the file row's help says so) — WhisperKit shares its 224-token decoder context between that prompt and generated tokens, and a dense recording can lose whole sentences to it, so Parakeet is the recommended engine for vocabulary boosting.
- **Terminology normalization** (`TerminologyNormalizer`, Settings → Transcription → Vocabulary → Canonical terminology) is a separate, engine-independent post-ASR pass: opt-in `Canonical => spoken variant | another variant` rules, applied to transcript segments after transcription regardless of which engine or vocabulary feature was used. The rules come from the Settings text area or, when one is selected, from an optional rules file (`AppSettings+TerminologyRules`, bookmarked like the vocabulary file, same syntax and limits). The file is read afresh in the per-job snapshot (`terminologyNormalizerForJob`), so an edit reaches the next job without a relaunch and never half of a running one; while a file is set the text area shows its contents read-only, as of the last read. A file that cannot be read, is not a regular file, is not UTF-8 or exceeds 64 KiB applies no rules, logs it and shows it in the Settings status: it never falls back to the text area, whose rules would then be applied without anyone being able to tell why.
- **An already-fetched WhisperKit model loads without the Hub.** `loadModel()` asks `WhisperKitLocalSnapshot` first and only downloads when nothing usable is there, because `WhisperKit.download` reaches huggingface.co before it inspects any local file (issue #736). That type carries the full mechanism and the condition under which it can be deleted again. The guarantee has a bound: the locator checks the CoreML bundles, not the tokenizer, which WhisperKit loads from a separate `models/openai/whisper-*` folder and otherwise fetches from the Hub, so a model folder copied in by hand without that cache still fails offline. Two consequences: a complete but stale copy is no longer revalidated on each load, and the normal online path no longer makes a Hub round trip per model file.
- **WhisperKit models live in `~/Library/Application Support/MeetingTranscriber/huggingface`, not the library default `~/Documents/huggingface`** (issue #640): Documents is synced by iCloud "Desktop & Documents", which uploaded every ~1 GB variant. `WhisperKitLocalSnapshot.downloadBaseLocation` is the single source of truth (`downloadBase` is the same path, created and excluded from Time Machine on first access, and is what writers use); it is passed to the download, to the locator (`HubApiWrapper(downloadBase:)`) and to `WhisperKitConfig`, where it also sets the tokenizer cache (`tokenizerFolder ?? downloadBase`); any new WhisperKit call must pass it too or it silently writes into Documents again. Not `Caches`, because a purge there would mean a silent gigabyte download or a failed load offline; the folder is excluded from Time Machine instead. `WhisperKitModelMigration` moves a complete, non-evicted copy of the variant being loaded (with its Hub download metadata under `.cache/huggingface/download/<variant>`) out of Documents on the next load, once per variant and process, on a background task the engine awaits through `WhisperKitModelSource.prepare` before its lookup, so `locateLocal` stays a pure path check. It copies the small `openai/whisper-*` tokenizers (staged under a temporary name, then renamed into place), never the whole shared `huggingface` folder, which other swift-transformers tools also use; anything it cannot move is downloaded afresh. Consequence worth knowing: the test suite goes through the production locator too, so `swift test` on a developer machine migrates that machine's models, and an older installed build will then download its model into Documents again. To keep a run off the real folders, give it another home: `CFFIXED_USER_HOME=<dir> swift test` resolves Application Support, Documents and Caches inside `<dir>`. Leave `HOME` alone: the Security framework finds the default keychain through it, and with `HOME` moved every keychain test fails. UserDefaults, keychains and TCC grants are per user and stay put, and an ffmpeg in `~/.local/bin` is no longer found unless linked in. The self-hosted CI test steps run that way, in a per-runner home from `.github/actions/runner-home`, which makes that link, because the Mini's runners share one account with each other and with the dev app; `RunnerHomeIsolationTests` fails a self-hosted run that does not.
- **Custom WhisperKit model** (Settings → Transcription → Model → "Custom model…"): another Hugging Face repository plus variant folder, or a model folder on disk. `AppSettings.whisperKitModelSelection` resolves it into a variant plus `WhisperKitModelOrigin` (`.hub(repoID:)` / `.localFolder`), and the engine treats the origin as part of the model's identity, because a fine-tune usually keeps its base model's folder name. `whisperKitModel` always stays a stock variant, and an unfinished custom model resolves to it. The Settings fields are `DraftTextField`s that write on Return or when the field is left (focus loss, or the field going away), not per keystroke, because the engine observer acts on every settings write; "Load Model" hands over a pending edit before it reads the selection, and so does closing the Settings window, which only hides it, so neither focus loss nor the field going away happens there (`WhisperKitCustomModelDrafts.settingsWindowWillClose`, only for the window with the Settings scene id and only while WhisperKit is selected and the custom model is on). Each field commits on its own, so changing the repository and then the variant is two commits, and in between the new repository is paired with the old variant. A value that is written is used as entered, so a wrong one fails the load with its reason rather than quietly running another model. A Hub origin reuses the local-first path above with its own repo root, and the download is accepted only when the returned folder is named exactly like the variant (`WhisperKitModelSource.downloadExactly`): WhisperKit matches `*<variant>/*`, so a tail-of-the-name variant would load once and never offline. A picked folder is never downloaded, so `WhisperKitLocalSnapshot.checkModelFolder` also requires the tokenizer files there, so that the folder is self-sufficient; no `tokenizerFolder` is passed, so WhisperKit uses the app's `downloadBase` in its place and looks in the app's tokenizer cache (`<downloadBase>/models/openai/whisper-<detected size>`) first, then at the top of `downloadBase`, then in the folder (and its own `models/openai/whisper-<size>`), and fetches from the Hub into that cache last. The folder goes through a security-scoped bookmark like the vocabulary file (fail-fast resolve for the validation line, full resolve for the load, stale repair at launch). A failed load keeps a path-free `WhisperKitEngine.loadFailureReason` (`WhisperKitLoadFailureReason`) that Settings shows under the status and `TranscriptionError.modelNotLoaded(reason:)` carries into the job error.
- `EngineController` (`@MainActor`) owns the engine instances + the active-engine selection (`activeTranscriptionEngine`, used by `PipelineQueue`) + the settings → engine language/vocabulary sync (up-front + reactive) + launch model preload. `AppState` exposes it as `engines`.

**Live captions (PoC):** "Enable live transcription during recording" in Settings → Transcription (`AppSettings.liveTranscriptionEnabled`, off by default; enabling downloads a ~0.6 GB model on first use behind a consent alert). Nested "Show caption overlay" (`AppSettings.liveCaptionsOverlayEnabled`, default on) hides `LiveCaptionsOverlay` without stopping the pipeline; `LiveCaptionsState` and `/state.liveCaptions` keep updating.
- A finalized line sets a reading hold of 0.3 seconds per word, with a 4-second minimum and an 6-second maximum. The maximum is 20 words at that rate, about what two lines show, so a final longer than its row is not held for words already clipped off it: before streaming finals were split into lines (below), a 104-word Parakeet EOU final kept the bar up for 31 seconds after the speech stopped. EOU and Nemotron finals are now at most 14 words, a 4.2-second hold, so the maximum only binds for re-transcribe finals. The 2-second fade starts only after that hold, and while a hypothesis is showing, not before it has gone 5 seconds without an update; content, hypotheses included, clears when the fade completes. The 5-second limit exists because no backend guarantees a final after a partial: `StreamingTranscriber` and the Nemotron session send nothing when the final decode is empty or throws, and the EOU session sends nothing when the final adds no text, so a hypothesis can be left standing until the next recording. The limit sits above the slowest partial cadence: Nemotron decodes every ~2.24 seconds and skips unchanged text, so two unchanged decodes leave 4.48 seconds between partials. A new partial or final restores full opacity; a final sets a fresh reading deadline. `LiveCaptionsState` exposes the fade target and schedules it with a cancellable task; the overlay animates opacity without periodically rebuilding caption text. The rolling final list still retains only two lines. Each row shows its complete text, capped at exactly two line heights of the row font, from its `NSFont` metrics, and clipped at the top, so a long row shows its newest words and cannot push the other channel's row out of the bar; a one-line row keeps its own height. The text is not trimmed to a word budget: dropping the oldest word on each partial re-wrapped both lines and moved every word, so the newest word had no fixed place. Untrimmed, the line breaks hold still, new words land at the end of the bottom line, and a full line leaves at the top. Hypothesis text is not cross-faded, because a cross-fade showed the old and new text overlaid: the `Text` uses `.contentTransition(.identity)`, so new words swap in at once, and only its position eases (0.2 s), so a full line slides out through the top of the clip instead of jumping. A single `Text` cannot fade one of its lines, and a fade band at the top edge would leave a faint copy of the hidden line on screen. Finals still fade in. A cap with slack above two lines shows the descenders of the hidden line as a strip. The speaker label sits next to the top visible line. The older final dims to 60 %; the newest final and both hypotheses stay at full opacity, because the newest final is usually still being read when the next speech starts. The whole caption box sits in a bottom-aligned viewport in the fixed-size panel, so overflow leaves at the top.
- `LiveCaptionLanguages` owns Nemotron's 39 trained languages, taken from the tokenizer's language tags, and the bare-code aliases `en` → `en-US`, `es` → `es-ES`, `pt` → `pt-BR`, `zh` → `zh-CN`, and `no` → `nb`. The aliases decide coverage only, not the prompt. The tokenizer's tags are all region-qualified (`<de-DE>`, `<ja-JP>`); the set keeps the region only where the tokenizer has more than one dialect, because the pickers produce bare codes, so a hand-set `ja-JP` is not recognised and uses re-transcribe. Lookup normalizes case and underscores. `LiveCaptionsGate.strategy(liveEnabled:engineLanguage:engineSupportsLive:)` is the pure decision function shared by `AppState`, `LiveTranscriptionCoordinator`, `LiveTranscriptionController`, and the Settings footnote and download-consent alert: disabled → off; English → `EouStreamingCaptionSession` (FluidAudio Parakeet EOU); a trained non-English language → `NemotronStreamingCaptionSession`/`NemotronAsrManager` (FluidAudio Nemotron multilingual); auto-detect or any other explicit language → re-transcribe via `StreamingTranscriber` when the engine supports it, else off. Of the picker languages, `id`, `ms`, `fa`, `fil`, `mk`, `yue` (WhisperKit) and `bs`, `be`, `sr` (Parakeet) are untrained and use re-transcribe; Nemotron's `auto` prompt produced unusable Indonesian (issue #928) and was not measured for the others. Overlay visibility is a separate UI AND (`overlayVisible`); it is not a strategy input.
- `NemotronAsrManager.resolvedLanguageCode` picks the key it hands to FluidAudio from the loaded model's `promptDictionary`, because FluidAudio's own lookup never adds a region and falls back to the `auto` prompt (`ja`, `zh`, `th`, `vi` and `he` have no bare key). Order: the configured code as an exact key when its prompt id is one a trained language uses, then the trained tag's key, then the tag with its likely region (`ja` → `ja-JP`). The first step keeps the model's own dialect for bare codes: `es` sends prompt 3, shared with `es-US`, and `pt` sends prompt 13, shared with `pt-PT`, as before this lookup existed; the model's bare `no` key (`no-NO`, 27) has no tokenizer tag, so `no` sends `nb`. A prompt key such as `id-ID` does not make Indonesian supported. With the shipped models every trained language resolves; if one did not, the manager logs the code and throws after the model load, and the controller's load-failure fallback takes over. `Tests/Fixtures/nemotron_prompt_metadata.json` is the shipped dictionary and tokenizer tags (identical for the latin and multilingual 2240 ms variants), and one table test pins strategy and prompt key for every picker language.
- Both streaming backends are engine-independent (drive their own FluidAudio models directly), so captions work even when the active `TranscribingEngine` has no live re-transcribe hook. `LiveTranscriptionController` wires the resolved per-channel pipeline to both `DualSourceRecorder` sinks and feeds `LiveCaptionsState`, which backs the `LiveCaptionsOverlay` window. A final is shown immediately with the channel label; asynchronous speaker matching updates only that still-retained final, so it cannot clear a newer hypothesis or restart its reading hold. `ModelWarmupQueue` serializes model warm-up loads so the ASR engine and streaming models don't compile/load concurrently at launch.
- EOU and Nemotron use `StreamingCaptionSplitter` to commit text-only lines at 14 complete words, keeping the next growing token in the hypothesis until a word boundary is known. EOU also commits an unchanged hypothesis after 0.7 seconds of ingested audio; the session checks this on every buffer, including buffers with no new ASR callback. The EOU manager's transcript is cumulative, so the splitter tracks a character offset and rebases it at a real EOU; reset and audio discontinuity clear the offset. Nemotron keeps its existing VAD speech-end and five-second force-flush boundaries and does not use unchanged text as a pause signal, because its decoder updates about every 2.24 seconds: its splitter is built with an infinite pause. Text splits do not finish or reset either model. The session seams expose no word-level audio timestamps, so a synthetic line receives the available unassigned audio once. A line with no audio left keeps the channel label: further lines from that same update, and a remainder finalized by an EOU whose timestamp lies before the last split. The pause rule commits the hypothesis as it stands, without holding back the last token: when the model later extends that token without a space, the extension starts the next line. On `two_speakers_en.wav` the model's own "featurement" (one final before the split) became "feature" and "ment" on two lines.
- `StreamingTranscriber` and `NemotronStreamingCaptionSession` make up to three VAD attempts per chunk (`vadAttemptsPerChunk`), then log and move on so a persistent VAD error cannot grow the backlog. `StreamingTranscriber` drops that chunk; Nemotron has already fed it to its cache-aware ASR stream and treats it as no boundary, so the stream is never spliced.
- Each channel feed retains up to 10 seconds of queued audio by duration (the `LiveTranscriptionController` default). The consumer awaits each ingest, so the queue fills for as long as one decode runs: the bound must exceed the slowest single decode plus the 0.8-second partial gate, or every such decode overflows and the reset discards the utterance it was decoding. On an 8 GB Mac with large-v3-turbo the slowest decode per run ranged from 5.8 to 15.5 s, so 10 s does not meet that rule there: it trades lag against loss, and holds up because overflow drops only the excess. Overflow drops oldest whole buffers until the queue fits again; the consumer resets the pipeline and app resampler before the next retained buffer so speech is never joined across a gap. Dropping only the excess, not the whole backlog, matters under sustained slower-than-real-time decoding: on that Mac, skipping to the newest buffer lost the full 10 s at every overflow, and in three of four paired runs over the same clip it lost 20 to 50 s where dropping oldest lost 1 to 5 s, at similar median lag (in the fourth, a 51 s decode stall made dropping oldest lose 62 s of the 130.7 s clip, about 47 %). Queue-dropped audio never reaches the pipeline; with Verbose Diagnostic Logging the stop-time flush logs each channel's dropped seconds and gap count. The bound is injectable; `LiveTranscriptionE2ETests` uses 60 seconds because it delivers its fixture much faster than real time. Retiring a feed at stop drains the retained pre-stop buffers before the pipeline final flush. The auto-detect re-transcribe path skips partials while queued and unprocessed audio exceeds the 0.8-second partial interval, so a machine that decodes slower than real time spends its decode time on finals; speech-end, five-second and recording-stop finals still run. EOU and Nemotron ignore the partial backlog hint but reset their stream state after a gap; a stall longer than the bound there loses the oldest audio instead of lagging.
- The caption panel moves on Option-drag from screen-coordinate mouse deltas; each proposed frame is clamped inside the visible frame of its owning screen. The move observer saves only while the left button is down, including after Option is released mid-drag, and stops at mouse-up. A dragged event handled with the button already up (queued behind a main-thread stall) is dropped, so the panel never stands where nothing was saved. macOS 27.2 relocates a panel dropped with the pointer on a screen edge, 2 to 190 ms after mouse-up (likely window tiling; not reproduced on 27.3 with a physical mouse or synthetic events); a move by the system within `dropRelocationWindow` (0.5 s) of a drag's mouse-up is undone by putting the panel back where it was dropped. The drop is the origin the drag last set, not the frame at mouse-up, which the system may already have moved; the mouse-up then puts the panel back at once.

**VAD preprocessing:**
- `FluidVAD` wraps FluidAudio Silero v6 for voice activity detection. When enabled (`AppSettings.vadEnabled`), silence is trimmed before transcription and timestamps are remapped back to the original timeline via `VadSegmentMap`.
- `PipelineQueue` holds a cached `FluidVAD` instance (reused across jobs). Pass `vadConfig: nil` to disable.
