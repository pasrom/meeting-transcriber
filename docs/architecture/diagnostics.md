# Diagnostics

What the audio-capture path logs, verbose and unconditional, and how to read it.

`AppSettings.verboseDiagnostics` (Settings → Advanced → Diagnostics → "Verbose Diagnostic Logging"; renamed from the legacy `audioDebugLogging` key, which is migrated on read) enables forensic logging in the audio-capture path:

- `[debug] Tap target: pid=… exe=… bundle=… audioObjectID=…` at start
- `[debug] Default output device: name=… uid=… transport=… rate=…` at start and on device change
- `[debug] Output device change → name=… uid=…` when system output device changes mid-capture
- `[debug] App audio RMS (5s): … dBFS, samples=…, totalBytes=…` every 5 s during capture — live signal whether the tap is delivering real audio or zero/noise
- `[debug] App audio capture stopping: totalBytes=…` at stop
- `[debug] Mic input device: name=… uid=… hwRate=… hwChannels=…` at mic capture start — the microphone the recording comes from: the device `AppSettings.micDeviceUID` pins when the pin took or could not be disproved, and the **system default input** when it demonstrably did not (nothing configured, the device absent, the set refused, or the unit answering with another device). A set that was accepted and could not be read back keeps naming the configured device: the acceptance is the only evidence there is, and falling back there would state the opposite of what was measured. (Issue #724.) **Do not "fix" this to report the device the input unit is bound to.** Measured on macOS 26: with nothing pinned, `AVAudioEngine` binds its input unit not to the microphone but to a private aggregate of its own, `CADefaultDeviceAggregate-<n>-0`, which follows the system default. Reporting that is strictly worse than the bug, because the question the line exists for is "built-in or headset". The unit is still read back, but as a watchdog on the pin, not as the identity.
- `[debug] Mic RMS (5s): … dBFS, samples=…` every 5 s during mic capture — `samples` counts at the **hardware** rate and across **all channels** (`frames * hwChannels`), not the 16 kHz mono written to the file. So `samples / (interval * hwChannels)` is a second, independent reading of the **capture rate**. That is corroboration, not identity: it separated the built-in mic (48 kHz) from AirPods in headset mode (24 kHz), but two devices can share a rate and a device's rate is not fixed, so it narrows the candidates rather than naming one. Omitting the channel divisor is how a stereo 24 kHz input reads as 48 kHz and gets mistaken for the built-in mic, which is the exact confusion this is used to settle.

**Unconditional** (not behind the toggle), because a silent-track report cannot be triaged by asking the user to have enabled logging beforehand, and because these are bounded rather than per-buffer (issue #672):

- `App audio tap: N PID(s) [names]` at start
- `System output device: … transport=…` at start
- `Aggregate input layout: anchorInputs=… inputStreams=…, tap is the last stream` at every tap build (start and each restart), a warning instead when the counts do not add up to "the anchor's inputs, then one tap stream" (issue #803, the mechanism behind #712 and #699; see `recording.md`). Read before the device starts, from the device the aggregate was bound to by UID.
- `App audio process state (start|zero run started|stop): exe=… pid=… object=… isRunningOutput=… outputDevices=…` — one line per tapped process. `isRunningOutput` separates a dead tap from a process that rendered nothing; it does **not** separate a silent far end from a dead tap, because a stream rendering zeroes still reports true. `outputDevices` says whether the process's output went to the output device or into some other device (a voice-processing aggregate, say) that the tap does not follow.
- `App audio device (start|watchdog check|zero run started|stop): aggregate=… running=… defaultOutput=… defaultOutputRate=… inputStreams=…` — one line per probe, from the same snapshot as the process-state lines. `inputStreams` is how many buffers the IOProc gets per callback, read after the device started; compared with the build-time `Aggregate input layout:` line it shows a layout that changed under a running tap. `running` is the aggregate's `kAudioDevicePropertyDeviceIsRunning`: `AudioDeviceStart` returning `noErr` says the object exists, not that IO runs, and no other line separates the two, so a report of "the tap was created and no buffer ever arrived" is otherwise undecidable (issue #693). The default output device's object id and nominal rate come from **one** read, so they always describe the same device: the aggregate binds its sub-device by UID, and a Bluetooth headset can change rate under it without the default output device changing, which nothing else notices. A failed read renders `?(status)` and never as a plausible value.
- `App audio: track has been at exact zeros for … s while buffers keep arriving` on entering a zero run, and the matching `signal returned after … s` on leaving. Capped at `SilentTrackObserver.maxEdgesPerRecording` edges per recording; the counters keep going past the cap so the stop line stays honest.
- `App audio at stop: bytes=… lastBufferAge=… lastEnergyAge=… zeroRuns=… longestZeroRun=…`. `lastEnergyAge=never` means the channel carried no non-zero sample at all, which is the signature of a tap that was never allowed to hear the app (issue #524), not of one that died.
- `App audio watchdog: …` lines, only when the opt-in silent-track watchdog is on (`AppSettings.silentTrackWatchdogEnabled`, Settings → Audio, default off; issue #672 part 2); with it off nothing below is logged and the `App audio at stop:` line is unchanged. The thresholds are the constants on `SilentTrackWatchdogPolicy`, the four that user-facing copy names coming from the public `SilentTrackWatchdogLimits` (`triggerZeroRunSeconds`, `minSecondsBetweenChecks`, `recoveryWindowSeconds`, `maxUnrecoveredRebuilds`, `maxRebuildsPerRecording`, `maxLoggedSkips`), and its doc comment carries the reasoning for each; `on (…)` at start prints the values in force. **A second trigger (issue #693):** with the watchdog on, a no-first-buffer probe (`NoFirstBufferProbeSchedule`, 5/30/120 s after the device started) that finds a tapped process rendering while the tap has delivered nothing opens the same check, and its rebuild runs through the same coordinator, arbiter, deadline and budgets; the check line says `no buffer N s after the device started` where a zero-run check says `exact zeros for N s`. No process rendering is an aggregate waiting under the autostart key for an idle target, which wakes by itself: declined, not rebuilt, and without spending the 60 s rate limit (the read was taken either way, and the limit bounds rebuilds), so the next probe is free to ask and every decline is logged within the skip-line budget rather than once per zero run. The re-check on the main queue asks this trigger's own question, still no buffer from the tap installed last (`the first buffer arrived before it could start` otherwise), and a probe whose read a first buffer, a teardown or a newer tap's arming overtook never reaches the watchdog at all (`SilentTrackDiagnostics.noBufferArming`). A rebuilt tap that delivers only zeros, in a recording that has carried no signal, is judged by the tick at the window like any other rebuild; only a tap that delivers nothing, or stops, is left to its deadline. Kept behind the opt-in on purpose: every rebuild is an exposure to the restart wedge, and whether a rebuild on the same headset recovers this fault is unmeasured on hardware. The teardown half of every rebuild runs inline on the main queue, unbounded (only the attempt is under the arbiter's deadline), so a block inside coreaudiod there is an app freeze rather than a lost channel; this trigger tears down an aggregate known not to be cycling, which is unmeasured against tearing down a working one. Cadence for a tap that never delivers: each rebuilt tap's 30 s probe lands inside the rate limit, so a fruitless rebuild costs about two minutes and the three the run allows about six, which the channel-silent warning precedes. A restart attempt discarded as stale, or as succeeded after the seal, takes the probes it armed with it. Per check: `requesting a rebuild (…) [pid=… object=… isRunningOutput=… outputDevices=…]` when a tapped process still reports output, or `isRunningOutput=false …, not rebuilding` once per zero run, or `check skipped, a process-state read is still outstanding` when another probe's read has not come back. `rebuild not started, <reason>` means the request was dropped on its re-check on the main queue (signal back, buffers stopped, the first buffer arrived, another tap installed, capture not running, a restart already in flight). After `rebuilding the tap … (rebuild N)` comes either `signal returned within … s of rebuild N` (when the latest non-zero sample the judging tick saw arrived, an upper bound on when signal first came back) or `rebuild N did not restore signal within … s`; signal that arrived after the recovery window is not credited to the rebuild, however late the tick that sees it. `rebuild N ended the channel, its restart gave up` means the rebuild's restart ran out of retries or wedged (issue #588); the watchdog stops there. `rebuild N installed a tap that delivered no buffer within … s; counted as not restoring signal` (or `stopped delivering buffers`) closes a rebuild no tick judged: the verdict comes from the 5 s tick, which only buffers drive, so a rebuilt tap that started without running a single IO cycle (the issue #693 failure) would otherwise leave the rebuild open until the recording stopped. Each tap installed while a rebuild is open is put on trial for it: its installation restarts the recovery window (so a restart's own wait and back-off are not charged to the tap) and arms a deadline of its own, two report intervals past the window, so a tap whose buffers do not pause for about a report interval around the end of the window is judged by a tick first and the deadline needs no signal from the IO callback. Only the tap installed last, and only while it is still installed, can be closed by its deadline: a tap torn down for a retry leaves the rebuild open for the next installation or for the restart's give-up. The deadline runs on its own queue, never behind a process-state read. An output device change while a rebuild is open, including one the restart path ignores or that lands while a restart has capture stopped, credits signal already back inside the window to the rebuild, and otherwise logs `output device changed during rebuild N; it will close without a verdict`; when that verdict is due, `rebuild N closed without a verdict, the output device changed while it was open` replaces it, and such a rebuild is not counted against the give-up budget. The watchdog carries on if buffers come back, and nothing tells the user yet. The give-up and `… rebuilds already in this recording; not rebuilding again` (the per-recording cap) appear at most once. At stop the summary gains `watchdogChecks= watchdogNoFirstBufferChecks= watchdogDeclined= watchdogDropped= watchdogRebuilds= watchdogRecoveries= watchdogGaveUp= watchdogCapped= watchdogEndedChannel= watchdogRebuiltTapStalled= watchdogSuperseded=`; `watchdogDropped` counts checks that ended without a decision or a rebuild (probe busy, dropped on re-check, refused by the restart path), so the checks add up. A give-up reaches the user as `ChannelFault.rebuildsExhausted` ("Capture Channel Silent"), not `gaveUp`, because the channel keeps capturing, and like `digitalSilence` only once the microphone corroborates that the call is live, and not at all if the app track carried signal since the give-up: the session flag is latched for the recording, so without that a far end that came back on its own while the microphone was quiet would be reported as silent the next time the user spoke; a later run of zeros on that track is reported as plain `digitalSilence`, after the "Warn after" window, because the give-up was about the run that ended. Whether a rebuild restores a dying tap is only answerable on hardware; these lines are how a field recording answers it.
- `Mic device set: …` / `Mic device not set: …` / `Mic device not adopted: …` at mic capture start, only when `AppSettings.micDeviceUID` pins a device. Four arms (issue #724), and the levels differ on purpose. A configured device that is merely absent, and one whose adoption could not be read back, are **default** level (a sleeping headset would otherwise log an error on every recording and bury the rest in the same filter); a refusal (`not set`, carrying the `OSStatus`) and an acceptance the unit did not honour (`not adopted`, carrying the device it is on instead) are **errors**. The last of those is why the read-back exists: `noErr` says the call was accepted, not that the unit moved. **No arm carries the device UID**, and a test enforces that: the line is unconditional, `PersistentDiagnosticLog` streams it to disk, and Settings offers that file as "a redacted log file" whose redaction *is* os_log privacy. An audio device UID is stable across boots and a USB one carries the serial, so it is named only in the verbose-gated `[debug] Mic input device:` line. Nothing acts on any of it yet: it is reported, not retried, and the user is not told.

The process-state reads run on their own queue (`com.meetingtranscriber.audiotap.diagnostics`), never on the write queue: that is the IOProc's delivery queue and `AppTapSession.destroy()` drains it with a `sync`, so a HAL read wedged there would wedge every teardown behind it (issue #588). One read at a time, so a wedged one costs a single parked thread rather than a pile.

View via Console.app, subsystem `com.meetingtranscriber.audiotap`. Off by default; turn on when investigating silent recordings or unusual routing.
