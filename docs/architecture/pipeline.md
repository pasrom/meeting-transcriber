# Pipeline and output

Concurrency, audio loading, job restore, protocol generation, record-only mode and output folders.

**Concurrency:**
- `WatchLoop` is `@MainActor`. Tests for this class must also be `@MainActor`.
- Both engines deduplicate concurrent loads with `SingleFlight`. Absent an explicit release, WhisperKit still finishes with the currently requested variant loaded or a failure for it, retrying variants superseded mid-load (issue #738). A model release invalidates the in-flight generation: its original caller may return without a loaded model, and a fresh caller that joined that stale flight retries. WhisperKit includes the generation in `LoadAttempt` alongside the variant/origin result; Parakeet's flight returns an `Int` generation. The load postcondition is therefore subject to explicit release, as described in [transcription engine model retention](transcription.md).
- The queue's processing flag alone is not the idle boundary: the lifetime observer also reads waiting and active jobs and whether recording or the stop-time caption flush is in flight. The queue records `lastDrainID` when processing ends with no waiting or active jobs, so even a drain completed within one actor turn survives coalesced observation callbacks. The observer retains the previous queue through its next turn so a queue replacement cannot hide that final marker. A queue drain while that combined state is busy cannot release models. Once it is idle, the selected model and cached batch VAD follow the retention policy in [transcription engine model retention](transcription.md). This boundary keeps one model warm across adjacent jobs and through a recording's buffered caption tail; it also applies deferred setting changes and, with idle unloading on, retires an inactive engine after a switch.
- `ClaudeCLIProtocolGenerator` runs the CLI (and its `--help` probe) through `BoundedProcess.run(timeout:onStop:)`: a timer on the suspending clock and the calling task's cancellation both stop the process (SIGTERM to its process group, SIGKILL after a grace), and the exit wait deliberately ignores cancellation, so the run returns or throws (`ProtocolError.timeout`, `CancellationError`) only once the CLI is gone and its folders can be removed. A run is `.timedOut` only if the CLI was still running at the limit. No pipe is read or written blocking, since a process the CLI started can hold one open after it exits: stdout/stderr are read through readability handlers into `AsyncStream`s that end at EOF or a short drain grace after the exit (stderr keeps its last 64 KB), and the prompt goes to stdin through a `DispatchIO` channel (SIGPIPE off) that is stopped with the CLI.

**Audio loading:**
- `AudioMixer.loadAudioAsFloat32()` uses a 3-tier fallback: `AVAudioFile` → `AVAsset` → `FFmpegHelper` (ffmpeg CLI).
- `loadAudioFromAVAsset()` extracts audio tracks via `AVAssetReader`, outputs 16kHz Float32 PCM. Rescue path only: `AVAudioFile` opens MP4/MOV too on current macOS, so this runs just when tier 1 throws on a non-MKV/WebM file. Its reader is configured like `streamResampleFile` (precise timing, little-endian float, source channels averaged in Swift), each option for a measured trap: an Ogg Vorbis track where `copyNextSampleBuffer()` blocks forever partway through, an AIFF read byte-swapped into NaN, a +3 dB fold against tier 1, and `DiscreteInOrder` decoding to silence with `status == .completed`. Sizing reads the AUDIO TRACK's duration, never the asset's: on a video container whose picture outlasts its sound the asset overstates the audio by seconds. That duration is untrusted (NaN for an indefinite one, absurd for a corrupt field), so the pre-allocation is capped rather than believed.
- `FFmpegHelper` detects ffmpeg binary (env var → `/opt/homebrew/bin` → `/usr/local/bin` → `~/.local/bin` → `/usr/bin`), cached via static let. Converts to 16kHz mono WAV via temp file. The run is bounded like the Claude CLI run (`BoundedProcess` + `ProcessOutput`); timeout → `ffmpegFailed("timed out after N s")`, cancel → `CancellationError`.
- Both `NSOpenPanel` type lists (batch import + voice enrollment) come from `AudioImportTypes`, not inline literals — the panels are manual-QA-only, so the pure type list is what tests can pin. Only MKV/WebM are ffmpeg-gated; AMR, 3GPP and Ogg (`.opus`/`.ogg`) decode natively and must stay out of `FFmpegHelper.ffmpegOnlyExtensions`, whose members skip `AVAudioFile`/`AVAsset` entirely.
- ffmpeg is optional — install via `brew install ffmpeg`. Status shown in Settings → About.
- The ffmpeg-tier tests (`FFmpegHelperTests` fixtures, the MKV/WebM legs of `WhisperKitE2ETests`) skip without ffmpeg, except on a GitHub runner, where they fail (`requireFFmpeg` / `ffmpegAvailableForTests` in the test helpers): a CI skip is how that tier once went untested in every lane. Every CI job that runs them first runs `.github/actions/setup-ffmpeg`, which installs a pinned, checksum-verified static build and exports it as `FFMPEG_BINARY`.
- **A finished job only relocates audio the app itself produced.** `AudioPersistencePolicy` decides per file: sources inside the staging dir (`AppPaths.recordingsDir`, where `DualSourceRecorder` writes) move into `<outputDir>/recordings`, sources already there stay put (moving would rename them under a fresh stamp and orphan recovery would re-pick them forever), and anything else is a user-picked import that is left untouched. Persisting an import would duplicate a file the user already has for no consumer: re-diarization and late naming read the `_16k.wav` sidecar, while orphan recovery and `ProcessedRecordingsLedger` only scan the staging dir. Consequence to keep in mind: a finished import leaves **no audio at all** in the output folder, only the transcript and the protocol. The 16 kHz sidecars live there while speaker naming is outstanding and `removeNamingData` deletes them once it resolves. The source staying in the user's folder is the archive. **A relocated job then carries the new paths.** `PipelineJob.recordRelocatedAudio` is the only writer of the three path fields after enqueue (they are `private(set)`), and the queue wrapper around it writes the snapshot itself rather than waiting for the next state transition: `generateProtocol` returns before its own `.generatingProtocol` transition when no protocol generator is configured, so with `protocolProvider == .none` there would be no transition to ride on. Without this the job named an emptied staging path, and quitting during the protocol call made the restore discard it: no protocol, no job, no notification. **A slot reports the destination only when the file is actually there** (this run moved it, or an earlier run already did); every other outcome, a failed move included, reports the source, because a path nothing can open would land in `ProcessedRecordingsLedger` while the real file waited in staging to be re-picked as an orphan. Consequences: the ledger records the destination for a relocated recording (inert, the orphan scan only reads staging). **The snapshot can lag the move, and the restore repoints.** The moves and their registry entry are one synchronous stretch, but `saveSnapshot` only schedules its write, so a kill right after stage 3, or inside it while a track is copied to another volume, restores a job that names staging files that are gone while some or all of its tracks sit in `<outputDir>/recordings`. `loadSnapshot` therefore runs `RelocatedAudioRepoint` before the missing-audio rule: a slot is pointed at `<outputDir>/recordings/<stem><suffix>` (as `.wav`, else as `.flac`: the kept containers, `RecordingFileSuffix.keptExtensions`) only when its path is in staging, that path is gone and the file there exists, with the stem stage 3 moves under: the `namingSlug` the run records on the job before the move, else the stem rebuilt from the job (`PipelineJob.artifactStem`: title, start time and the job's own short ID; the start renders in the current time zone, so after a zone change only the recorded one matches). Only a stem that ends in the job's short ID is tried (an AI-title rename can set `namingSlug` to the bare title, and a rename only follows the move), so a duplicate job that named the same staging files never takes another job's recording. A zone change after a kill inside the move can leave one recording under two stems: the tracks moved before the kill under the old one, the rest moved by the restored run under the new one. A job another queue still runs is left alone; the in-flight rule drops it right after. Every slot is checked, not only the mix: the moves go mix, app, mic, and a job repointed on its mix alone would run with its app track missing. When the mix slot moved, the recording sidecar still in staging is moved under the mix's stem as well, because stage 3 takes it only from a job that still names the staging mix (a failed move is logged), and the repointed files plus the sidecar under that stem, moved now or by stage 3 before the kill, are registered for retention under the queue's output folder with the job's start time; stage 3 registers only what its own run moves, so a recording cut off mid-move would otherwise keep its mix and sidecar unlisted for good. Registering is idempotent, so the common case (everything moved and listed) adds nothing. The adoption of a replaced queue's jobs does not repoint: it reads them from memory, which the move updated. The missing-audio rule then fires only on files that are really gone, failed relocations, snapshots written before jobs carried their relocated paths, and relocated audio the repoint cannot find: under an output folder the setting has moved away from since the kill or that is unreachable at launch, or under a stem an AI-title rename changed just before it (the rename's snapshot write is asynchronous too, and the old paths are already in the output folder, so they are not staging paths). That rule also logs what it discards now, and rewrites the snapshot so the same dead entry is not re-read and re-logged on every launch.
- **A dual-source recording the pipeline processes keeps a recording sidecar**, `<stem>_recording.json`: the `RecordingSidecar` type, schema and version record-only writes. `WatchLoop.enqueueRecording` writes it beside the staging mix (`RecordingSidecar.writeRecordingSidecar`); a recording with only one track has no offset to keep and gets none. Stage 3 (`persistAudioToOutput`, which also relocates a cancelled job's recording) moves it out of staging with the mix, under the job's stem, with `files` rewritten to the relocated names (a restore that repoints a job whose mix had already moved takes it the same way); the AI-title rename carries it (`ArtifactRenamePlan`) and rewrites `files` again. A re-import (`PipelineController.enqueueFiles`, `RecordingSidecar.readForReimport`) reads `_meta.json` first and this file second, so the re-imported job keeps the recorded mic offset, mute times, title, participants and meeting start instead of taking the offset as zero, which shifted the dual-track merge and the echo detector's lag search (issue #980). Orphan recovery takes the offset, and only the offset, from the sidecar still beside a staging mix whose job was lost (`RecordingSidecar.recordedMicDelay`, read in the detached scan), and only when its `files.mix` names that mix, so a recording never takes another one's sidecar; without a readable one the recovered job runs at zero as before. Its title, participants and start stay the recovery's own, since the start would change the job's stem. **It is not called `_meta.json` on purpose:** processed recordings land in the same `<outputDir>/recordings/` folder as record-only output, and the sidecar is what a record-only write commits last to say a recording is complete. A consumer of that folder can take any new `*_meta.json` as a recording waiting for it (the record-only e2e lanes in `scripts/` find their output exactly that way; the external fleet consumer is not in this repository), so under that name a processed recording could be processed a second time. The offset only matters when the raw delay is positive: `MicDelayNormalisation` pads the app track of a mic-first recording on disk and reports zero, so for those a re-import at zero was already right. A failed write is logged and costs only that re-import's metadata.
- **Recording retention (issue #723)** deletes relocated audio once it is due: Settings → Output → Recording Retention (`AppSettings.recordingRetentionEnabled`, off by default; `recordingRetentionDays`, where 0 means as soon as the outputs exist). It deletes only what `RecordingRetentionRegistry` (`retained_recordings.json` in `logDir`) lists and never lists the folder, so imports, record-only captures and audio from before the feature are out of reach by construction, not by a rule. An entry also lists the recording sidecar that moved with the mix; a due entry deletes it after the tracks (and on the next pass when one was cut short between them), and it never counts as audio (`RecordingRetentionPolicy.isRecordingSidecar`), so a leftover sidecar cannot keep an entry whose tracks are gone: one that is not due yet is dropped and leaves the sidecar, as it leaves a transcript. Stage 3 writes the entry at the move, for exactly the files `persistAudioToOutput` reports it moved in this run (never a destination that already held a file whose source is gone: it may be the user's), whatever the setting says; the restore's repoint (see the relocation paragraph above) also registers the files it points a job at, which are such destinations, because it takes only a file under the job's own stem in place of a staging file that is gone; a relocation under a different root starts a second entry for the job: a run restored after a quit finds its audio already relocated and moves nothing, so an entry left for `.done` would never be written for it, and switching retention on later must cover what was recorded while it was off. The entry becomes eligible where the run's output is produced, never at `.done` (`PipelineQueue.markOutputWritten`, which also requires a regular file with content): when `generateProtocol` saves the protocol, when it finds no generator (the transcript is the output then), when a restore finishes a job whose protocol was already written, and when the auto-names are accepted with no provider (`finishWithAcceptedAutoNames`). Everything else that reaches `.done` keeps its audio without a rule of its own: a failed protocol call, a job finished because its naming data was lost across a restart, and a late confirm that could not read the transcript or write the names into it (the transcript is the unconfirmed draft then). A protocol-only resume after a quit does not count the transcript even with no provider now, since the run it continues was generating a protocol. Marking before `.done` is safe because the policy keeps every entry a job that is not done holds. The output is checked again at delete time: one the user deleted since keeps the audio. The exception is a Notion export set to replace the local Markdown: once it succeeds and the local copy is removed, the entry is marked `outputExported` and the page counts as the output. Days count from `artifactStartTime`, the stamp in the file name. `RecordingRetentionPolicy.decide` keeps a whole entry when any of its tracks belongs to a job that is not done (a run reads `_app.wav`/`_mic.wav` too, and the in-flight claims name a run's staging mix path, not the relocated files, so the current queue's unfinished jobs are the real protection; a queue is only replaced once all its jobs are finished), and keeps an entry whose root is missing, or whose `recordings` folder cannot be listed (the sandbox can show the root and hide its files), since an unplugged drive read as "files gone" would drop the entry and make the files permanent. Under a live scope on one output folder, an entry under another root is kept as unreachable. Only files directly in the root's `recordings` folder are deleted, both as written and with symlinks resolved (the containing folder, plus the file itself when it exists). An entry whose audio is all gone is dropped whether or not it ever became eligible, as long as its root is reachable. Only regular files are deleted: a listed path that is now a folder or a link is skipped and stays listed. Decisions and registry writes run on the main actor, the deletes on `RecordingFileDeleter` (Spotlight stall class, as with the snapshot writer), with a nested scope opened on the root the queue holds a scope on; if it cannot be opened the pass deletes nothing. Every delete is rechecked on the main actor right before it runs (the entry still lists the path, the settings still make it due, no unfinished job of the queue that started the pass or of the current one holds any of its tracks, the registry is saved), a deleted path is forgotten only for the entry the decision was made for, and no pass deletes while the last registry write failed. The AI-title rename repoints the entry, also for files a failed rollback left under the new name. Passes run when a job reaches `.done`, after a queue rebuild, one second after either setting stops changing; every pass acts on the settled settings, so a value the stepper only passes through never acts, while switching off or lengthening the period applies at once; at launch and hourly; a pass with retention off, or with nothing listed, returns at once and logs nothing; every other pass that gets past saving the registry logs one info line with counts per outcome and keep reason, due files next to deleted files, and never a path (file names carry the meeting title), since a pass that only keeps would otherwise leave no trace that it ran; before a built queue is installed, a pass reads the output folder with `OutputDirectoryResolver.current` (never `resolve()`, which reports an unreachable folder) and the queue snapshot itself and keeps every track a job in it names, because the placeholder queue has not loaded it; an unreadable snapshot skips the pass. A registry file that exists but cannot be read or decoded is moved aside to `.unreadable` instead of being overwritten.
- **Recording storage limit** caps the disk space of the recordings `RecordingRetentionRegistry` lists: Settings → Output → Recording Retention (`AppSettings.recordingStorageLimitEnabled`, off by default; `recordingStorageLimitGB`, default 10, at least 1, decimal gigabytes). It runs as a second step of every retention pass (`RecordingRetention.sweepBySize`), independent of the age toggle, and deletes only what the age rule could delete with a period of 0 days (`RecordingRetentionPolicy.decide` with `days: 0`), so every safety rule above applies unchanged: outputs written and still present, not held by an unfinished job, inside the root's `recordings` folder, root reachable. The total counts every listed file it can reach, eligible or not, so recordings still waiting for their outputs, or whose notes file is gone, can keep it over the limit; under a scope on one output folder, entries under another root neither count nor go. A track an entry lists and holds on disk both as WAV and as its FLAC (FLAC compression below: between naming the copy and unlinking the WAV, and after a failed unlink or a quit in between) counts once, as the FLAC, when a run is expected to remove that WAV (`RecordingCompaction.pairResolves`, asked through `RecordingRetention.pairResolves`): the entry is the compactor's entry in work, or it is still marked as owed FLAC while the setting is on and the probe has not ruled FLAC out (the rule `markFinished` marks by, so the launch pass, which runs before the probe answers, counts a pair a quit left once) and the entry is under the folder of the run going on or the folder the next run would get (`PipelineController.compactionOutputRoot`: the built queue's, else `outputDirectory.current`, read once per measure and once per deleted recording). Otherwise both files count, so the limit stays a cap on what is on disk: with the setting off, with no FLAC, or under an earlier output folder no run works under (only a pass that holds no scope counts those). Known limit: a marked pair a run passes over (due under the age rule, held by a job that ended in an error), or one in a session whose probe never answers, still counts once while that lasts; so does a marked pair whose unlink failed, or met after the setting was switched off and on, or after a run returned early because its scope did not open, which waits for the next job reaching `.done` or the next launch, the only automatic events that start a run, or for Compress Existing Recordings below. The delete still removes both, and what it frees is the recording's counted bytes before less what its entry, as it is then, counts after, so a WAV whose unlink failed while its FLAC went counts in full again and keeps the warning, and a FLAC the compactor wrote meanwhile still counts. **No recording is deleted without a warning given after it became deletable.** Over the limit, `RecordingStorageLimitPolicy.step` notifies and stores a `RecordingStorageWarning` (time, limit, scope root; `recordingStorageLimitWarning` in the settings defaults, so a restart neither repeats the notification nor restarts the wait). A stored warning counts only for a limit at least as low as the one it named and for the same scope root: lowering the limit or switching output folders warns again. After `gracePeriod` (24 hours, wall-clock: a launch after a longer quit deletes on its first pass) the next pass, at most an hour later, deletes the oldest recordings whose notes were saved by the warning (`eligibleAt <= since`) until the total is at or under the limit. If the total is still over afterwards and a recording that became deletable after the warning could go, the pass warns again and that recording waits out a grace period of its own; without this, a total held over by recordings that cannot go would delete each new recording seconds after its notes are saved, and an old recording whose notes only succeed on a retry seconds after the retry. While recordings that cannot go keep the total over, each recording that becomes deletable after the stored warning leads to a new notification (at most one per 24 hours while the settings stay unchanged), with the same wording even though the total will not reach the limit. Coverage goes by `eligibleAt`, which is set once: a recording whose `eligibleAt` is already set but that `decide` kept for another reason — a missing notes file, a track held by an unfinished job, or an unreachable output folder (such as an earlier folder on an unplugged drive while recordings in the current one keep the total over in a pass that counts every folder) — was not a candidate when the warning was given, counts as covered by it, and can go on the first pass after that reason ends. Once the delete time has passed, Settings says the covered recordings are being deleted rather than naming a time in the past. A delete that fails keeps the warning, so the next pass retries without a new notification. The delete loop rechecks the live limit before each recording, so raising it mid-pass stops the deletes once the new limit is met. Falling under the limit clears the warning on the next pass, and the next time over warns again. Switching the limit off clears it at once, in the setting itself (`AppSettings.recordingStorageLimitEnabled`), rather than on the next pass, which may not come before a queue is built when the age rule is off too. The grace period starts whether or not the notification was delivered; Settings shows the pending deletion instead (`AppSettings.recordingStorageStatus`, set after every size pass: usage, the part that cannot be deleted yet, and the stored warning with its delete time). The size pass also drops entries whose files are all gone, as the age pass does, since the age pass does not run while it is off, and logs one info line per pass with the step, total, limit and counts. Raising the limit and switching off apply at once; lowering it and switching on wait for the settings to settle, as for the age rule.
- **Kept recordings can be converted to FLAC after `.done`** (`RecordingCompaction`; Settings → Output → Recording Storage, `AppSettings.compressKeptRecordings`, off by default). Stage 3, capture, staging, crash recovery, record-only output and imports stay WAV: a WAV cut off by a crash is repaired by rewriting its header, a cut-off FLAC stream is not. **Reach:** only what `RecordingRetentionRegistry` lists, never a folder's contents, so the population is retention's (no imports, no record-only, nothing from before the registry, nothing of a job cancelled before its audio reached the output folder, whose relocation never registers; a job cancelled after the move is listed and converted); the one folder listing is the sweep of its own leftovers below. **When:** a job reaching `.done` with the setting on marks its entry under the queue's output folder (no mark, and no run, for a job with no entry there or while the probe reports no FLAC) (`RetainedRecording.awaiting`, a set of `CompactionKind`, decoded absent as empty and tolerant of names it does not know, not written while empty) and starts a run; a run at launch, after the codec probe, takes every marked entry, so a quit mid-encode only delays a recording. Unmarked entries (recordings from before the setting was on) are left to **Compress Existing Recordings** (Settings → Output → Recording Storage; `PipelineController.compressExistingRecordings`), a request kind on the same `run` (`RecordingCompactionPlan.Request.everyEntry`), so it has the selection, the per-track sequence and every safety rule below, and adds no conversion path of its own. It takes every entry that still lists a WAV track (and a marked one with none left, so its mark goes), works with the setting off and is not stopped by switching it, and clears the `flac` mark of what it finishes. The confirmation names the count (`compressibleCount`: by name only, entries under the current folder with a WAV track in its `recordings` folder that no unfinished job holds and retention does not delete now, so no file of a recording is looked at on the main actor; before a queue is built the output folder's bookmark is resolved, as the Output tab already does) and says what is not touched: imports, record-only output, recordings from before the registry, recordings of jobs cancelled before their audio reached the output folder and files renamed by hand (never listed), and that other output folders, entries in use and evicted iCloud files are skipped. The button is disabled with its reason while the probe has not confirmed FLAC or nothing is eligible, and from the confirmation until its own run returns, which shows the tracks done out of those its selection found and a Cancel that stops only that run, after the step it is in (a copy not yet committed is removed; what is not converted stays WAV and a later press continues), or drops it from the queue while it still waits behind an automatic run, which finishes, and records a cancelled summary (`cancelRequestedRun`; the rows follow `RecordingCompaction.requestedRun`: idle, waiting or running). An automatic run shows no Cancel there and leaves the button usable. Every request, the first included, waits in `RecordingCompactionPlan.Backlog`, which keeps the user's run apart from the kinds automatic requests owe: each request runs once, in a fixed order: a kind that must come before any encode (a mix drop) first, then the user's run, then the FLAC pass it covers, so cancelling the user's running pass never loses an automatic request it was queued with, and a kind other than FLAC is never merged away. Before a queue is built, every call reads the snapshot's held tracks while the user's run is queued, not only one that has work: queued requests run with the newest context, and a weaker one would strip those tracks from the user's run. The loop takes the next pass out in the same turn it starts it, and each pass is its own task, so a cancel ends that pass, not the loop: a request that joins after a cancel (a meeting finishing meanwhile) still runs. The recording sidecar is rewritten when the run changed a name of the entry, cancelled or not, and for a finished entry that was marked (a crash before the rewrite leaves the mark); only the mark waits for a finished entry, and an entry the run did nothing to keeps its sidecar unread. A request that arrives while a run is going queues behind it, so there is never a second run beside the first and a later request never replaces the user's (see the backlog above). Its summary (`RecordingCompaction.lastRequestedRun`: converted files, bytes saved as each WAV's size less its copy's, and the count per skip reason, or why it could not start: no FLAC, FLAC not yet confirmed, a scope that did not open, or before a queue is built an unreadable snapshot) stays in Settings until the next run; the run also logs its line as `Compaction run (every entry)`. A quit during this run leaves the entry in work in one of the tracked crash states below; with the setting off no launch run finishes it (it is not marked), and both copies of a track left both listed then count in full under the storage limit until the action is pressed again. The `mixDrop` kind is defined so that action needs no second migration; nothing sets it. An automatic run does nothing but its sweep unless the setting is on and the launch probe (`KeptRecordingCodecProbe`: one second of synthetic 16-bit PCM encoded, decoded and compared in the temp folder, and checked to start with `fLaC`; in memory only, `unavailable` only for a compressor failure, a copy that is not native FLAC, or the format codes `AVAudioFile` throws for what it cannot write (`'fmt?'`, `'typ?'`), and `unknown` for anything else, since `AVAudioFile` reports file-system failures such as a full volume (-40) or an unwritable folder (-54) in its own domain too (measured on macOS 27), logged as the codec name and shown in `/state.recordingStorage`) found FLAC; with no FLAC the Settings toggle is disabled with the probe's reason (while it is off; one left on can still be switched off) and no entry is marked, since nothing would clear the mark. One run at a time, a later request queued behind it; it holds one security scope on the object the caller resolved for its whole length (a queue rebuild can release the queue's own mid-run), and works only on entries under the output folder it was given. **Selection** (main actor): skipped whole, mark kept, are entries a job that is not done holds, entries under another root, entries whose root is missing (an unplugged drive), and entries retention would delete now. Only listed `_mix/_app/_mic.wav` paths directly in `<root>/recordings` are tracks, read from the entry again before each one, so a rename during the run is followed. A track that reads as gone counts as deleted by hand only with `ENOENT` and while the output folder is there; another stat error, an output folder that went away (an unplugged drive), or a `recordings` folder that is not there or cannot be listed keeps the mark (a volume detached from a custom mount point leaves the mount point as an empty folder, so the root looks present; the condition retention uses before it takes files for gone). The WAV is removed only while its copy is there, checked right before. A track stopped because the entry gave its WAV up (a rename the run then follows, a newer recording on the path) keeps no mark either. The entry's paths, and per track the copy's final and partial names, are the compactor's in-work set, which the controller adds to retention's `heldPaths`, so a pass that comes due mid-run keeps the entry whole, under the age rule and the storage limit alike. **Per track:** off the main actor the file facts (a regular file, not a link or folder; not evicted, i.e. an iCloud item not `.current` or a file with `SF_DATALESS`; free space at least the size plus 64 MB; the size and modification time), then `KeptRecordingCompressor.prepare`: integer PCM up to 24 bit only, and only a RIFF `WAVE` file whose chunks account for the whole file with one `data` chunk the size of the frames read (a `data` chunk counting fewer frames than the file holds would compress as the shorter recording; refused for good, the WAV kept; metadata chunks of any size pass), chunked encode into the hidden `.<stem>_<track>.partial.flac` beside the WAV (it has to end in `.flac`: given a name ending in `.partial` `AVAudioFile` writes FLAC inside a CAF without an error, measured on macOS 27, and the decode check passes on that, so `prepare` also checks for `fLaC`), decode and compare every sample by stream position (a read can return short), owner-only mode and the WAV's dates best effort, `F_FULLFSYNC` falling back to `fsync`, cancellation checked in the loops and again after the await. Then one main-actor turn with no suspension: the registry is saved, the entry still lists the WAV (an AI-title rename or a newer recording on the path ends that), no unfinished job holds the entry, it is not due, the WAV's size and time are unchanged, the partial is the file that was verified (device, inode and size taken right after `prepare`) and the final name is free; the final `.flac` is registered **before** the rename creates it (a failed save forgets it again), the partial is renamed with `RENAME_EXCL` (never over an existing file; on a volume without it a hard link takes the name, which also fails on a taken one, and the partial name is removed; where the link is refused for any reason but a taken name, the name is checked and renamed in the same turn), and a finished job still in the queue that names the WAV is pointed at the copy. A failed recheck removes the partial. Then the folder is flushed the same way, the entry is checked to still list the WAV and no unfinished job to hold it, the WAV is unlinked, and only then forgotten. After an entry's tracks its `_recording.json` gets `files` rewritten on the main actor to the listed names, read from the entry so a rename in between writes the moved sidecar and never recreates one under the old name; the schema stays version 3, `files.mix` is always written, and `files` holds the names as of the last rewrite, so a named file can be absent. **The mark** goes when every track is done or failed for a reason that would repeat (not integer PCM, a link or folder, a final name taken by an unlisted file, which is never touched, a header that disagrees with the file size, a mismatch, no native FLAC); it stays for one that can change (evicted, unreadable, low space, a failed sync, a write or read error such as a full disk, a failed recheck, a cancel, or the setting switched off, which stops an automatic run after the step it is in). **Every crash point is tracked:** after the encode, a hidden partial beside a listed WAV (the next attempt replaces it); after register, a listed name that does not exist yet (tolerated by `decide`; the next run registers again and renames); after the rename, WAV and FLAC both listed (retention deletes both when due; the next run checks the copy against the WAV and removes the WAV); after the unlink, a listed WAV that is gone (the next run forgets it). A partial left by a run that was cut off is removed by the sweep at the start of every run once it is 24 hours old by its status-change time (it carries the WAV's dates, so its modification time is the recording's age), whatever the setting says, only under the current output folder and only names of exactly that pattern. **Limits, accepted:** the last recheck and the unlink are not one step, so a re-import of the WAV in that gap fails on a missing file while the recording is kept as FLAC; a job that ended in `.error` holds its tracks, so its recording stays WAV until it is dismissed and an explicit run converts it; the WAV and its copy exist together for the length of one encode, one track at a time. An older build pairs no FLAC tracks on import, its AI-title rename leaves FLAC tracks under the old stem, and it drops `awaiting` on its next registry write; its retention still deletes FLAC tracks by their listed paths.

**Restoring an interrupted job:**
- `ProtocolResumePolicy.decide(interruptedIn:transcriptExists:hasNamingSlug:hasProtocol:)` is the pure decision the snapshot restore makes for a job it found mid-run: `.resumeProtocolOnly` generates the protocol from the transcript already on disk, `.finish` only applies the terminal transition, `.fullRun` re-runs everything.
- **It keys on the stage the job was interrupted in, never on "a transcript exists":** `saveTranscriptDraft` writes one in stage 1, so a job killed during diarization has a draft without speaker labels, and resuming from it would publish that draft. Only `.generatingProtocol` means the transcript on disk is the finished one. A late re-diarization therefore runs in full by design: its transcript is the segmentation the user asked to redo.
- The marking is the snapshot state itself, held in memory as `protocolResumeDispositions` for the span of one restore. Nothing is persisted: a quit before the resume runs degrades to a full run rather than losing anything, and a second persisted field would have to be kept in step with the state it was derived from.
- **A failed or interrupted Notion export, or failed meeting notes, come back at launch.** `restorePendingNotionExports` builds the first queue when every saved job is `done` and at least one is held after completion (`isHeldAfterCompletion`: a pending export, or notes to retry), so the retry row appears without a watch start. Any other saved job keeps waiting for a user action, because building the queue would resume it; a notes retry that was still waiting at the quit is such a job, and runs once something builds the queue.
- **A Notion retry sends the page it would have sent the first time, from the local backup alone.** With the transcript option on, the export appended the transcript under `## Full Transcript` in the file it saved, and `MarkdownToNotionBlocks` reads that section back into the same toggles, so the retry passes no separate transcript. The retry replaces the page's blocks, so a job whose option was on and whose backup has lost that heading is refused with a fixed warning and stays failed: sending it would swap a page that has the transcript for one that has none.
- Why it is not merely a saving: a late confirm transits `.generatingProtocol` too, so a full run there re-diarizes, discards the names the user just confirmed and parks the job back in the dialog they just closed.

**Speaker naming window:**
- **The naming window opens by itself only while `AppSettings.autoOpenSpeakerNaming` is on (default).** A job with naming data parks at `.speakerNamingPending` either way; the setting only gates the two automatic `.showSpeakerNaming` posts, after processing (`PipelineQueue+Stages`) and on snapshot restore (`PipelineQueue+Recovery`). The queue reads it through a closure, like `echoCancellationEnabled`, so a change applies without restarting watching. Off, `onSpeakerNamesWaiting` takes the window's place at both points and `PipelineController` turns it into a "Name Speakers" user notification; the restore site is needed because a job restored already pending never makes the transition again. The user then gets back to it through the menu bar's "Name Speakers...", and the stale cleanup on launch still accepts the auto-names once `AppSettings.staleNamingTimeout` has passed. A window the user opens, or the return from a late re-run they started, is not gated (and does not notify). A waiting job holds the queue meanwhile; see **Unnamed meetings on launch**.

**Retrying a failed job:**
- **The menu offers Retry from state alone, never from a file check.** `canRetryJob` runs in the view body on every render, and the recording can sit on a network or removable volume where `fileExists` blocks the main thread. `retryJob` checks the file itself on every click; one that finds it gone adds a fixed sentence to the job's error text (once) and changes nothing else, and the offer stays, so a volume that comes back is retryable. See the comments on `canRetryJob`.

**Unnamed meetings on launch:**
- **A meeting left waiting for names longer than `AppSettings.staleNamingTimeout` gets the automatic names at the next launch.** `loadSnapshot` runs `cleanupStalePending()`, which reads the timeout through a closure (`staleNamingMaxAge`, wired in `PipelineController.makeQueue`) and accepts the auto-names for every `.speakerNamingPending` job whose wait, counted from `namingDeadlineStart`, is longer: 1 day (the default, and the only value before the setting existed), 7 days, or never. It runs only on launch, so a meeting is resolved at the first start after its time is up, not the moment it expires. `cleanupStalePending(maxAge:)` is the ungated form tests use. **A waiting job also holds the queue.** `.speakerNamingPending` keeps `PipelineController.canReplaceQueue` false, so `rebuild()` (every watch start) and `rebuildIfOutputFolderChanged()` skip, and engine, diarization and output-folder changes reach new meetings only once the job is named or skipped, or after a relaunch (whose first rebuild runs on the empty placeholder queue). With the naming window opening by itself that wait is usually minutes; with it off (`autoOpenSpeakerNaming`) it lasts until the meeting is named or the timeout passes, and with Forever nothing bounds it, which the Settings caption says.

**Protocol generation:**
- `ProtocolGenerating` protocol with two implementations: `ClaudeCLIProtocolGenerator` and `OpenAIProtocolGenerator`.
- `AppSettings.protocolProvider` enum (`.claudeCLI` / `.openAICompatible` / `.none`) selects the provider. `.none` skips LLM generation and saves the transcript only.
- `AppSettings.protocolLanguage` string (default `"German"`) is substituted into the prompt as `{LANGUAGE}`. `{MEETING_DATE}` (`YYYY-MM-DD`) and `{MEETING_TIME}` (`HH:mm`) resolve from a captured recording start time, or to `Unknown` for imports and recovery jobs. Only a captured recording start adds the authoritative meeting-metadata preamble, so processing time is never presented as a meeting time.
- `ProtocolGenerator.loadPrompt()` loads custom prompt from `AppPaths.customPromptFile` (`~/Library/Application Support/MeetingTranscriber/protocol_prompt.md`), falls back to built-in default.
- `OpenAIProtocolGenerator` supports any OpenAI-compatible HTTP API (Ollama, LM Studio, llama.cpp, etc.).
- **Saved OpenAI-compatible connections** (`AppSettings.openAIConnections`, `AppSettings+OpenAIConnections.swift`): each keeps an endpoint, model, sampling overrides and key placement, and its API key in its own Keychain item (`openAIKeyAccount(for:)`). The live `openAI*` settings stay what the generator, `/v1` and Fetch Models read: selecting a connection copies its values into them and `openAIAPIKey` reads the selected connection's item, so nothing downstream knows connections exist. The selected connection's stored copy is refreshed from the live values only when the selection changes. A first launch turns the existing setup into "Default", which keeps the original `openAIAPIKey` Keychain item. Only a launch with nothing stored under the key migrates; a value of another type counts as unreadable. The list is decoded one connection at a time (`OpenAIConnection.decodeList`), so one this build cannot read (an unknown enum value or a missing required field, as after a downgrade from a newer release) drops only itself; an unknown extra field decodes and is only stripped at the next write; the stored data is first copied to `openAIConnectionsUnreadable` (once, never overwritten) because the next write loses the dropped entries. When none is readable, the app starts one fresh connection with its own empty Keychain item instead of migrating: the live values then belong to whichever connection was selected, and migrating would pair the original key with its endpoint. Downgrading to a release from before connections reads only the original item and the live values, so with any connection but "Default" selected it sends Default's key to the selected endpoint; this is accepted and stated in the release notes, because avoiding it means rewriting the original item on every switch and key edit. A new connection copies the current settings but not the key. The last connection cannot be deleted; deleting one removes its key. Add, Rename and Delete each ask first (`OpenAIConnectionPrompts`): Add and Rename with a name prompt, Delete with a confirmation that names the connection, and a Rename or Delete confirmed after the selection changed does nothing. The Settings key field commits a typed key to the connection being left before the switch (`OutputSettingsView.switchConnection`). A stored selection that matches no saved connection loads the first one at launch, so its key never goes to the previous endpoint. A Fetch Models result that arrives after the selection changed is dropped, so it cannot replace the new connection's model. A job reads the connection selected when its notes step starts, not when it was queued, as it did before connections existed.
- **A provider failure does not fail the job.** `generateProtocol` catches it, adds the warning "Protocol generation failed — transcript saved", records the kind of failure as `PipelineJob.notesFailure` (`MeetingNotesFailure`) and the job still reaches `.done` with its transcript. The kind is decided in the catch, where the error case is known; the provider's own message, which for an HTTP error carries part of the server's response body, goes to the log only. The done notification then reads "Meeting Notes Failed" with the kind's fixed sentence, instead of "Transcript Saved", while `AppSettings.notifyOnMeetingNotesFailure` is on (the default). Only a Claude CLI error that asks to run `/login` adds the sign-in hint, so another provider's authentication error never sends the user to the CLI. Standard urgency: the failure is over when it is announced, and a batch import with a signed-out CLI posts one per job. `PipelineQueue.doneNotification` holds the choice of text.
- **Failed notes can be retried from the transcript, never by a full run.** A `.done` job with `notesFailure` and a `transcriptPath` (`hasRetryableMeetingNotes`) is held like a pending Notion export (`isHeldAfterCompletion`): no 60-second cleanup, kept by the snapshot restore and the queue adoption, kept even when its audio is gone, and `restorePendingNotionExports` builds the first queue for it at launch. Being held, it lets its audio sidecars go when it finishes, as an export does: the retry reads the transcript. The menu offers **Retry Meeting Notes** per job and **Retry All Meeting Notes (N)** from two such jobs; `/v1` offers the same (see `docs/automation-api.md`). `retryMeetingNotes` (`PipelineQueue+MeetingNotes`) sets `PipelineJob.generatesNotesOnly` and puts the job back to `.waiting`; `runPipeline` sends such a job to `generateNotesOnly` ahead of the protocol-only resume and the engine guard. The marker is on the job, not in the queue's memory, so a retry still waiting at a quit is a notes retry after the relaunch too (once the queue is built, as above), and the restore does not drop it for missing audio. A notes-only run claims no audio in `InFlightRunRegistry`, since it never reads it, so another run of the same recording does not refuse it. The failure stays on the job until notes are saved (`updateJobState` clears it on `.done` with a saved protocol, with the warnings that described the job without notes), so a retry that fails again, or meets a provider switched to None while it waited, stays on offer; with the provider None the retry is refused, and a provider switched to None while it waited records `.noProvider`. That is `generateProtocol`'s own answer (`ProtocolGenerationOutcome`), not the factory asked a second time after it returned: a provider switched off while the model writes leaves the reason that call recorded, and a job whose notes appeared meanwhile gets no failure. A transcript that cannot be read when the job runs records `.transcriptUnreadable`, so the notification names the reason of this run. A notes-only run that saved nothing is announced as "Meeting Notes Not Saved", never "Transcript Saved"; the marker stays on the job for that until the notes are saved. For the same reason its "Meeting Notes Failed" notification ends after the kind's sentence: "The transcript is saved" follows only for a run that saved one, so not for a notes-only run and not for `.transcriptUnreadable`. The retry passes the speaker names the failed attempt had (`notesSpeakerNames`) to the Notion export. Notes already next to the transcript, under the job's stem or the transcript's name, are never replaced: checked on the click, when the job runs and again after the model call, each ends the offer with a warning; after the call it says that the notes were generated and not written. A transcript that cannot be read leaves the offer in place with a warning. Nothing retries by itself.
- **Notes for a transcript the user picks run the notes step only.** *Generate Meeting Notes from Transcript…* (and `POST /v1/jobs/notes/generate`) goes through `PipelineController.generateNotes(fromTranscripts:)`, which refuses while the provider is None and, for the menu only, names skipped files in a notification (`/v1` gets them in its response), to `PipelineQueue.enqueueNotes(fromTranscripts:)`: one job per `.txt`, with `generatesNotesOnly`, `transcriptPath` set to the file, `notesBasename` to its name and `meetingStartTime` from a leading `yyyyMMdd_HHmm`. `runPipeline` sends such a job to `generateNotesOnly`, the same as a notes retry, so it never transcribes, also after a relaunch. The notes are saved as `<notesBasename>.md` beside the file; `namingSlug` stays nil, because it names the speaker-naming sidecars and removing a job deletes by it, and a picked transcript can share its name with a meeting still waiting for names. Nothing is read on the main actor at enqueue: a file is taken by its extension and its size (above zero, at most `maxTranscriptBytes`, a guard rather than a measured bound; the size of the file a symbolic link points at, which is what the read reads), and read off the main actor when its job runs. A transcript given twice, or already waiting in a notes-only job, is queued once. The file is the user's, not a run's output, so the job keeps the raw transcript and never renames by the AI title whatever the settings say. A transcript that has notes is skipped at enqueue, and notes that appear while the job waits or while the model runs are never replaced. A job that ends without notes says why on the job and in its notification ("Meeting Notes Not Saved" or "Meeting Notes Failed", never "Transcript Saved"), and one that ended for a missing provider or an unreadable transcript can be retried like failed notes. Not in the App Store build: the menu item is compiled out, and `/v1` is not there either, since the sandbox grants the picked file only and not the folder the notes would go to. The panel enables `.txt` files only (`TranscriptPanelDelegate`): `.plainText` alone would also admit Markdown.
- **Transcript output options** (Settings → Output): `AppSettings.includeFullTranscriptInProtocol` (append the verbatim transcript to the generated Markdown) and `AppSettings.saveRawTranscriptSeparately` (keep the standalone `.txt`) both default to `true` for backward compatibility, and are captured per job at enqueue time so a settings change mid-queue doesn't retroactively affect jobs already running. The raw transcript is retained regardless of the setting whenever protocol generation is disabled, fails, or the job ends in an error — losing the only transcription is worse than an unwanted file. `AppSettings.useAITitleForFilenames` (default `false`, captured per job the same way) renames a job's artifacts to a snake_case slug of the title in the generated protocol's heading, without the timestamp, once a protocol exists (`ArtifactRenamePlan` plans it, `PipelineQueue.renameJobArtifacts` runs it). Every artifact is named from the closed suffix lists, never found by a directory prefix scan, a stem is only taken when none of its artifacts exist in `protocols/` or `recordings/` (else `_<shortID>` is appended), nothing is ever overwritten, and a failed move is undone so the job keeps its old stem. A bracketed or placeholder heading, or one with no alphanumerics, keeps the timestamped name.

**Record-only mode:**
- When `AppSettings.recordOnly` is true, a stop (`WatchLoop.stopAndEnqueue`, through `writeRecordOnlyOffMain`, off the main actor) moves the dual-source WAVs into `<settings.effectiveOutputDir>/recordings/` and writes a `<basename>_meta.json` `RecordingSidecar` next to them, skipping the entire post-processing pipeline (VAD, transcription, diarization, protocol generation). Both call sites, auto-detected meetings (`handleMeeting`) and manual recordings (`stopManualRecording`), flow through the same branch. The destination is wrapped in `startAccessingSecurityScopedResource()` to honour user-picked Output Folder bookmarks (relevant for the App Store sandboxed build).
- **Mic mute times:** `MicMuteTimeline` holds them in seconds of the mic track, `MicMuteLog` saves them at each toggle for crash recovery (the orphan scan attaches it to a recovered job and deletes it for any finished stem it skips that no job or run has; the log of a recovered recording stays beside it until `persistAudioToOutput` moves the mix out of staging, because the adopted job is on disk only once its snapshot write lands and a process that dies before then adopts the recording again), and `PipelineJob.micMuteIntervals` carries them. The recorder, a reimport and orphan recovery each attach them only to a job with a mic track, since without one the mix is transcribed and it holds the far end (a lone `_mix.wav` is a paired group too). A reimport of `_mix.wav` and `_mic.wav` without the `_app.wav` the sidecar names gets none either, for the same reason (`RecordingSidecar.micMuteIntervals(app:mic:)`). `PipelineJob.init` clips, orders and merges them (`sanitized`), since a sidecar on disk can hold anything. Mic text more than `TimestampedSegment.maxMutedShare` inside a mute is dropped because the engines are not trusted on long zeroes, and each mute renders as `[Mic muted 12:03–12:15]`. A dual-source recording muted throughout resolves to `DualTrackViability.appOnlyMicMuted`, which skips mic transcription and diarization; a microphone-only one fails with `micMutedThroughout`.
- Sidecar JSON contains: `version` (currently `RecordingSidecar.currentVersion = 3`), `title`, `appName`, `startedAt`/`stoppedAt` (ISO 8601, reconstructed from `recordingStart` uptime), `participants`, `micDelaySeconds`, `micMuteIntervals`, `trigger`, `files` (basenames only). Optional `app` / `mic` filenames are omitted when nil.
Suffix constants live as static lets: the audio-file suffixes on `RecordingFileSuffix` (`mix = "_mix.wav"`, `app`, `mic`, and the raw-temp `appRaw`/`legacyAppRaw`), and the sidecar suffix on `RecordingSidecar.filenameSuffix = "_meta.json"`.
- **Track names in two containers.** Staging only ever holds WAV, so `RecordingFileSuffix.stripSuffix` and everything that scans staging (orphan recovery, record-only, `PairedRecordingResolver.resolve` with its default) take WAV names only, and a `.flac` there is never a track. A track kept in the output folder can also be `.flac` (`RecordingFileSuffix.compressed`); the readers of that folder take both through `keptTrack(of:)`: an import (`PipelineController.enqueueFiles`, its panel summary, and so `/v1/jobs`), so a compressed `_app.flac` and `_mic.flac` of one stem are one dual-source job as their WAVs were, and a stem with both spellings of a track takes the WAV; the AI-title rename (`ArtifactRenamePlan`, which carries the `.flac` names and counts them as taking a stem); the recording sidecar move, which keeps each file name's own container; and the restore repoint above.
- `trigger` (`auto` | `manual`, added in version 2) says which call site produced the recording, so a fleet consumer can discard a very short *auto* capture as a false trigger while always processing an equally short *manual* one — duration alone cannot tell those apart. A browser meeting is `auto`: the detector initiates it and the consent prompt only gates it. Every field added after version 1 must decode as optional, because `RecordingSidecar.read` is a `try?` and one unrecognised value would otherwise discard the *entire* sidecar on the reimport path.
- Intended for fleet topologies where macOS clients capture and a separate machine (e.g. Linux GPU host) processes the audio via Syncthing or similar.
- Menu bar: the small red dot is rendered as a **persistent overlay** (`MenuBarIcon.image(..., recordOnlyOverlay:)`) on top of *whatever* primary badge `BadgeKind.compute(...)` would otherwise show — idle, recording, transcribing, etc. — so the mode is always visible. Permission overlay (red exclamation) takes precedence when both apply, since a permission problem actually breaks recording. Settings tabs dim Transcription / Protocol / VAD / Diarization sections via `View.recordOnlyDisabled(_:)` and show a banner in the General tab pointing at the active output dir.
- Sidecar write failures notify the user via `NotificationManager` (injected as `any AppNotifying` on `WatchLoop`) since record-only does not transition state to `.error`.

**Output folder fallback:** when the chosen output folder's bookmark stops resolving (unplugged drive, unmounted share, deleted folder), output goes to `~/Downloads/MeetingTranscriber` and the user is told once. `AppSettings.outputDirectoryResolution` says which happened (`.defaultLocation` / `.custom` / `.fallback`, the last one naming the chosen path read from the bookmark bytes); `effectiveOutputDir` is its URL and stays a pure read. `OutputDirectoryResolver` (owned by `PipelineController`, shared with `WatchingController`) is the only thing that notifies, and it is called only where a destination is captured: `PipelineController.makeQueue()` (by value, for every job the queue runs) and the record-only destination closure (per write). Once per episode, keyed on the bookmark; a folder that resolves again or a new choice re-arms it. Views and the poll must never call `resolve()`. `AppSettings.init(defaultOutputDir:)` exists so tests can point the fallback away from the real Downloads folder; a test that resolves to the production default is one step from writing into it.
