# Pipeline and output

Concurrency, audio loading, job restore, protocol generation, record-only mode and output folders.

**Concurrency:**
- `WatchLoop` is `@MainActor`. Tests for this class must also be `@MainActor`.
- Both engines deduplicate concurrent loads with `SingleFlight`. Absent an explicit release, WhisperKit still finishes with the currently requested variant loaded or a failure for it, retrying variants superseded mid-load (issue #738). A model release invalidates the in-flight generation: its original caller may return without a loaded model, and a fresh caller that joined that stale flight retries. WhisperKit includes the generation in `LoadAttempt` alongside the variant/origin result; Parakeet's flight returns an `Int` generation. The load postcondition is therefore subject to explicit release, as described in [transcription engine model retention](transcription.md).
- The queue's processing flag alone is not the idle boundary: the lifetime observer also reads waiting and active jobs and whether recording or the stop-time caption flush is in flight. The queue records `lastDrainID` when processing ends with no waiting or active jobs, so even a drain completed within one actor turn survives coalesced observation callbacks. The observer retains the previous queue through its next turn so a queue replacement cannot hide that final marker. A queue drain while that combined state is busy cannot release models. Once it is idle, the selected model and cached batch VAD follow the retention policy in [transcription engine model retention](transcription.md). This boundary keeps one model warm across adjacent jobs and through a recording's buffered caption tail; it also applies deferred setting changes and, with idle unloading on, retires an inactive engine after a switch.
- `ClaudeCLIProtocolGenerator` runs the CLI (and its `--help` probe) through `BoundedProcess.run(timeout:onStop:)`: a timer on the suspending clock and the calling task's cancellation both stop the process (SIGTERM to its process group, SIGKILL after a grace), and the exit wait deliberately ignores cancellation, so the run returns or throws (`ProtocolError.timeout`, `CancellationError`) only once the CLI is gone and its folders can be removed. A run is `.timedOut` only if the CLI was still running at the limit. No pipe is read or written blocking, since a process the CLI started can hold one open after it exits: stdout/stderr are read through readability handlers into `AsyncStream`s that end at EOF or a short drain grace after the exit (stderr keeps its last 64 KB), and the prompt goes to stdin through a `DispatchIO` channel (SIGPIPE off) that is stopped with the CLI.

**Audio loading:**
- `AudioMixer.loadAudioAsFloat32()` uses a 3-tier fallback: `AVAudioFile` → `AVAsset` → `FFmpegHelper` (ffmpeg CLI).
- `loadAudioFromAVAsset()` extracts audio tracks via `AVAssetReader`, outputs 16kHz Float32 PCM. Rescue path only: `AVAudioFile` opens MP4/MOV too on current macOS, so this runs just when tier 1 throws on a non-MKV/WebM file. Its reader is configured like `streamResampleFile` (precise timing, little-endian float, source channels averaged in Swift), each option for a measured trap: an Ogg Vorbis track where `copyNextSampleBuffer()` blocks forever partway through, an AIFF read byte-swapped into NaN, a +3 dB fold against tier 1, and `DiscreteInOrder` decoding to silence with `status == .completed`. Sizing reads the AUDIO TRACK's duration, never the asset's: on a video container whose picture outlasts its sound the asset overstates the audio by seconds. That duration is untrusted (NaN for an indefinite one, absurd for a corrupt field), so the pre-allocation is capped rather than believed.
- `FFmpegHelper` detects ffmpeg binary (env var → `/opt/homebrew/bin` → `/usr/local/bin` → `~/.local/bin` → `/usr/bin`), cached via static let. Converts to 16kHz mono WAV via temp file. The run is bounded like the Claude CLI run (`BoundedProcess` + `ProcessOutput`); timeout → `ffmpegFailed("timed out after N s")`, cancel → `CancellationError`.
- Both `NSOpenPanel` type lists (batch import + voice enrollment) come from `AudioImportTypes`, not inline literals — the panels are manual-QA-only, so the pure type list is what tests can pin. Only MKV/WebM are ffmpeg-gated; AMR, 3GPP and Ogg (`.opus`/`.ogg`) decode natively and must stay out of `FFmpegHelper.ffmpegOnlyExtensions`, whose members skip `AVAudioFile`/`AVAsset` entirely.
- ffmpeg is optional — install via `brew install ffmpeg`. Status shown in Settings → About.
- The ffmpeg-tier tests (`FFmpegHelperTests` fixtures, the MKV/WebM legs of `WhisperKitE2ETests`) skip without ffmpeg, except on a GitHub runner, where they fail (`requireFFmpeg` / `ffmpegAvailableForTests` in the test helpers): a CI skip is how that tier once went untested in every lane. Every CI job that runs them first runs `.github/actions/setup-ffmpeg`, which installs a pinned, checksum-verified static build and exports it as `FFMPEG_BINARY`.
- **A finished job only relocates audio the app itself produced.** `AudioPersistencePolicy` decides per file: sources inside the staging dir (`AppPaths.recordingsDir`, where `DualSourceRecorder` writes) move into `<outputDir>/recordings`, sources already there stay put (moving would rename them under a fresh stamp and orphan recovery would re-pick them forever), and anything else is a user-picked import that is left untouched. Persisting an import would duplicate a file the user already has for no consumer: re-diarization and late naming read the `_16k.wav` sidecar, while orphan recovery and `ProcessedRecordingsLedger` only scan the staging dir. Consequence to keep in mind: a finished import leaves **no audio at all** in the output folder, only the transcript and the protocol. The 16 kHz sidecars live there while speaker naming is outstanding and `removeNamingData` deletes them once it resolves. The source staying in the user's folder is the archive. **A relocated job then carries the new paths.** `PipelineJob.recordRelocatedAudio` is the only writer of the three path fields after enqueue (they are `private(set)`), and the queue wrapper around it writes the snapshot itself rather than waiting for the next state transition: `generateProtocol` returns before its own `.generatingProtocol` transition when no protocol generator is configured, so with `protocolProvider == .none` there would be no transition to ride on. Without this the job named an emptied staging path, and quitting during the protocol call made the restore discard it: no protocol, no job, no notification. **A slot reports the destination only when the file is actually there** (this run moved it, or an earlier run already did); every other outcome, a failed move included, reports the source, because a path nothing can open would land in `ProcessedRecordingsLedger` while the real file waited in staging to be re-picked as an orphan. Consequences: the ledger records the destination for a relocated recording (inert, the orphan scan only reads staging), and the restore's missing-audio rule now fires only on genuinely missing files, failed relocations, and snapshots written before this existed. That rule also logs what it discards now, and rewrites the snapshot so the same dead entry is not re-read and re-logged on every launch.
- **Recording retention (issue #723)** deletes relocated audio once it is due: Settings → Output → Recording Retention (`AppSettings.recordingRetentionEnabled`, off by default; `recordingRetentionDays`, where 0 means as soon as the outputs exist). It deletes only what `RecordingRetentionRegistry` (`retained_recordings.json` in `logDir`) lists and never lists the folder, so imports, record-only captures and audio from before the feature are out of reach by construction, not by a rule. Stage 3 writes the entry at the move, for exactly the files `persistAudioToOutput` reports it moved in this run (never a destination that already held a file whose source is gone: it may be the user's), whatever the setting says; a relocation under a different root starts a second entry for the job: a run restored after a quit finds its audio already relocated and moves nothing, so an entry left for `.done` would never be written for it, and switching retention on later must cover what was recorded while it was off. The entry becomes eligible where the run's output is produced, never at `.done` (`PipelineQueue.markOutputWritten`, which also requires a regular file with content): when `generateProtocol` saves the protocol, when it finds no generator (the transcript is the output then), when a restore finishes a job whose protocol was already written, and when the auto-names are accepted with no provider (`finishWithAcceptedAutoNames`). Everything else that reaches `.done` keeps its audio without a rule of its own: a failed protocol call, a job finished because its naming data was lost across a restart, and a late confirm that could not read the transcript or write the names into it (the transcript is the unconfirmed draft then). A protocol-only resume after a quit does not count the transcript even with no provider now, since the run it continues was generating a protocol. Marking before `.done` is safe because the policy keeps every entry a job that is not done holds. The output is checked again at delete time: one the user deleted since keeps the audio. The exception is a Notion export set to replace the local Markdown: once it succeeds and the local copy is removed, the entry is marked `outputExported` and the page counts as the output. Days count from `artifactStartTime`, the stamp in the file name. `RecordingRetentionPolicy.decide` keeps a whole entry when any of its tracks belongs to a job that is not done (a run reads `_app.wav`/`_mic.wav` too, and the in-flight claims name a run's staging mix path, not the relocated files, so the current queue's unfinished jobs are the real protection; a queue is only replaced once all its jobs are finished), and keeps an entry whose root is missing, or whose `recordings` folder cannot be listed (the sandbox can show the root and hide its files), since an unplugged drive read as "files gone" would drop the entry and make the files permanent. Under a live scope on one output folder, an entry under another root is kept as unreachable. Only files directly in the root's `recordings` folder are deleted, both as written and with symlinks resolved (the containing folder, plus the file itself when it exists). An entry whose audio is all gone is dropped whether or not it ever became eligible, as long as its root is reachable. Only regular files are deleted: a listed path that is now a folder or a link is skipped and stays listed. Decisions and registry writes run on the main actor, the deletes on `RecordingFileDeleter` (Spotlight stall class, as with the snapshot writer), with a nested scope opened on the root the queue holds a scope on; if it cannot be opened the pass deletes nothing. Every delete is rechecked on the main actor right before it runs (the entry still lists the path, the settings still make it due, no unfinished job of the queue that started the pass or of the current one holds any of its tracks, the registry is saved), a deleted path is forgotten only for the entry the decision was made for, and no pass deletes while the last registry write failed. The AI-title rename repoints the entry, also for files a failed rollback left under the new name. Passes run when a job reaches `.done`, after a queue rebuild, one second after either setting stops changing; every pass acts on the settled settings, so a value the stepper only passes through never acts, while switching off or lengthening the period applies at once; at launch and hourly; a pass with retention off, or with nothing listed, returns at once and logs nothing; every other pass that gets past saving the registry logs one info line with counts per outcome and keep reason, due files next to deleted files, and never a path (file names carry the meeting title), since a pass that only keeps would otherwise leave no trace that it ran; before a built queue is installed, a pass reads the output folder with `OutputDirectoryResolver.current` (never `resolve()`, which reports an unreachable folder) and the queue snapshot itself and keeps every track a job in it names, because the placeholder queue has not loaded it; an unreadable snapshot skips the pass. A registry file that exists but cannot be read or decoded is moved aside to `.unreadable` instead of being overwritten.

**Restoring an interrupted job:**
- `ProtocolResumePolicy.decide(interruptedIn:transcriptExists:hasNamingSlug:hasProtocol:)` is the pure decision the snapshot restore makes for a job it found mid-run: `.resumeProtocolOnly` generates the protocol from the transcript already on disk, `.finish` only applies the terminal transition, `.fullRun` re-runs everything.
- **It keys on the stage the job was interrupted in, never on "a transcript exists":** `saveTranscriptDraft` writes one in stage 1, so a job killed during diarization has a draft without speaker labels, and resuming from it would publish that draft. Only `.generatingProtocol` means the transcript on disk is the finished one. A late re-diarization therefore runs in full by design: its transcript is the segmentation the user asked to redo.
- The marking is the snapshot state itself, held in memory as `protocolResumeDispositions` for the span of one restore. Nothing is persisted: a quit before the resume runs degrades to a full run rather than losing anything, and a second persisted field would have to be kept in step with the state it was derived from.
- **A failed or interrupted Notion export comes back at launch.** `restorePendingNotionExports` builds the first queue when every saved job is `done` and at least one has a pending export, so the retry row appears without a watch start. Any other saved job keeps waiting for a user action, because building the queue would resume it.
- **A Notion retry sends the page it would have sent the first time, from the local backup alone.** With the transcript option on, the export appended the transcript under `## Full Transcript` in the file it saved, and `MarkdownToNotionBlocks` reads that section back into the same toggles, so the retry passes no separate transcript. The retry replaces the page's blocks, so a job whose option was on and whose backup has lost that heading is refused with a fixed warning and stays failed: sending it would swap a page that has the transcript for one that has none.
- Why it is not merely a saving: a late confirm transits `.generatingProtocol` too, so a full run there re-diarizes, discards the names the user just confirmed and parks the job back in the dialog they just closed.

**Speaker naming window:**
- **The naming window opens by itself only while `AppSettings.autoOpenSpeakerNaming` is on (default).** A job with naming data parks at `.speakerNamingPending` either way; the setting only gates the two automatic `.showSpeakerNaming` posts, after processing (`PipelineQueue+Stages`) and on snapshot restore (`PipelineQueue+Recovery`). The queue reads it through a closure, like `echoCancellationEnabled`, so a change applies without restarting watching. Off, `onSpeakerNamesWaiting` takes the window's place at both points and `PipelineController` turns it into a "Name Speakers" user notification; the restore site is needed because a job restored already pending never makes the transition again. The user then gets back to it through the menu bar's "Name Speakers...", and the stale cleanup on launch still accepts the auto-names once `AppSettings.staleNamingTimeout` has passed. A window the user opens, or the return from a late re-run they started, is not gated (and does not notify). A waiting job holds the queue meanwhile; see **Unnamed meetings on launch**.

**Retrying a failed job:**
- **The menu offers Retry from state alone, never from a file check.** `canRetryJob` runs in the view body on every render, and the recording can sit on a network or removable volume where `fileExists` blocks the main thread. `retryJob` checks the file itself on every click; one that finds it gone adds a fixed sentence to the job's error text (once) and changes nothing else, and the offer stays, so a volume that comes back is retryable. See the comments on `canRetryJob`.

**Unnamed meetings on launch:**
- **A meeting left waiting for names longer than `AppSettings.staleNamingTimeout` gets the automatic names at the next launch.** `loadSnapshot` runs `cleanupStalePending()`, which reads the timeout through a closure (`staleNamingMaxAge`, wired in `PipelineController.makeQueue`) and accepts the auto-names for every `.speakerNamingPending` job whose wait, counted from `namingDeadlineStart`, is longer: 1 day (the default, and the only value before the setting existed), 7 days, or never. It runs only on launch, so a meeting is resolved at the first start after its time is up, not the moment it expires. `cleanupStalePending(maxAge:)` is the ungated form tests use. **A waiting job also holds the queue.** `.speakerNamingPending` keeps `PipelineController.canReplaceQueue` false, so `rebuild()` (every watch start) and `rebuildIfOutputFolderChanged()` skip, and engine, diarization and output-folder changes reach new meetings only once the job is named or skipped, or after a relaunch (whose first rebuild runs on the empty placeholder queue). With the naming window opening by itself that wait is usually minutes; with it off (`autoOpenSpeakerNaming`) it lasts until the meeting is named or the timeout passes, and with Forever nothing bounds it, which the Settings caption says.

**Protocol generation:**
- `ProtocolGenerating` protocol with two implementations: `ClaudeCLIProtocolGenerator` and `OpenAIProtocolGenerator`.
- `AppSettings.protocolProvider` enum (`.claudeCLI` / `.openAICompatible` / `.none`) selects the provider. `.none` skips LLM generation and saves the transcript only.
- `AppSettings.protocolLanguage` string (default `"German"`) is substituted into the prompt as `{LANGUAGE}`. `{MEETING_DATE}` (`YYYY-MM-DD`) and `{MEETING_TIME}` (`HH:mm`) resolve from a captured recording start time, or to `Unknown` for imports and recovery jobs. Only a captured recording start adds the authoritative meeting-metadata preamble, so processing time is never presented as a meeting time.
- `ProtocolGenerator.loadPrompt()` loads custom prompt from `AppPaths.customPromptFile` (`~/Library/Application Support/MeetingTranscriber/protocol_prompt.md`), falls back to built-in default.
- `OpenAIProtocolGenerator` supports any OpenAI-compatible HTTP API (Ollama, LM Studio, llama.cpp, etc.).
- **Transcript output options** (Settings → Output): `AppSettings.includeFullTranscriptInProtocol` (append the verbatim transcript to the generated Markdown) and `AppSettings.saveRawTranscriptSeparately` (keep the standalone `.txt`) both default to `true` for backward compatibility, and are captured per job at enqueue time so a settings change mid-queue doesn't retroactively affect jobs already running. The raw transcript is retained regardless of the setting whenever protocol generation is disabled, fails, or the job ends in an error — losing the only transcription is worse than an unwanted file. `AppSettings.useAITitleForFilenames` (default `false`, captured per job the same way) renames a job's artifacts to a snake_case slug of the title in the generated protocol's heading, without the timestamp, once a protocol exists (`ArtifactRenamePlan` plans it, `PipelineQueue.renameJobArtifacts` runs it). Every artifact is named from the closed suffix lists, never found by a directory prefix scan, a stem is only taken when none of its artifacts exist in `protocols/` or `recordings/` (else `_<shortID>` is appended), nothing is ever overwritten, and a failed move is undone so the job keeps its old stem. A bracketed or placeholder heading, or one with no alphanumerics, keeps the timestamped name.

**Record-only mode:**
- When `AppSettings.recordOnly` is true, `WatchLoop.enqueueRecording()` moves the dual-source WAVs into `<settings.effectiveOutputDir>/recordings/` and writes a `<basename>_meta.json` `RecordingSidecar` next to them, skipping the entire post-processing pipeline (VAD, transcription, diarization, protocol generation). Both call sites — auto-detected meetings (`handleMeeting`) and manual recordings (`stopManualRecording`) — flow through the same branch. The destination is wrapped in `startAccessingSecurityScopedResource()` to honour user-picked Output Folder bookmarks (relevant for the App Store sandboxed build).
- Sidecar JSON contains: `version` (currently `RecordingSidecar.currentVersion = 2`), `title`, `appName`, `startedAt`/`stoppedAt` (ISO 8601, reconstructed from `recordingStart` uptime), `participants`, `micDelaySeconds`, `trigger`, `files` (basenames only). Optional `app` / `mic` filenames are omitted when nil.
Suffix constants live as static lets: the audio-file suffixes on `RecordingFileSuffix` (`mix = "_mix.wav"`, `app`, `mic`, and the raw-temp `appRaw`/`legacyAppRaw`), and the sidecar suffix on `RecordingSidecar.filenameSuffix = "_meta.json"`.
- `trigger` (`auto` | `manual`, added in version 2) says which call site produced the recording, so a fleet consumer can discard a very short *auto* capture as a false trigger while always processing an equally short *manual* one — duration alone cannot tell those apart. A browser meeting is `auto`: the detector initiates it and the consent prompt only gates it. Every field added after version 1 must decode as optional, because `RecordingSidecar.read` is a `try?` and one unrecognised value would otherwise discard the *entire* sidecar on the reimport path.
- Intended for fleet topologies where macOS clients capture and a separate machine (e.g. Linux GPU host) processes the audio via Syncthing or similar.
- Menu bar: the small red dot is rendered as a **persistent overlay** (`MenuBarIcon.image(..., recordOnlyOverlay:)`) on top of *whatever* primary badge `BadgeKind.compute(...)` would otherwise show — idle, recording, transcribing, etc. — so the mode is always visible. Permission overlay (red exclamation) takes precedence when both apply, since a permission problem actually breaks recording. Settings tabs dim Transcription / Protocol / VAD / Diarization sections via `View.recordOnlyDisabled(_:)` and show a banner in the General tab pointing at the active output dir.
- Sidecar write failures notify the user via `NotificationManager` (injected as `any AppNotifying` on `WatchLoop`) since record-only does not transition state to `.error`.

**Output folder fallback:** when the chosen output folder's bookmark stops resolving (unplugged drive, unmounted share, deleted folder), output goes to `~/Downloads/MeetingTranscriber` and the user is told once. `AppSettings.outputDirectoryResolution` says which happened (`.defaultLocation` / `.custom` / `.fallback`, the last one naming the chosen path read from the bookmark bytes); `effectiveOutputDir` is its URL and stays a pure read. `OutputDirectoryResolver` (owned by `PipelineController`, shared with `WatchingController`) is the only thing that notifies, and it is called only where a destination is captured: `PipelineController.makeQueue()` (by value, for every job the queue runs) and the record-only destination closure (per write). Once per episode, keyed on the bookmark; a folder that resolves again or a new choice re-arms it. Views and the poll must never call `resolve()`. `AppSettings.init(defaultOutputDir:)` exists so tests can point the fallback away from the real Downloads folder; a test that resolves to the production default is one step from writing into it.
